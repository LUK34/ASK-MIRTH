# HL7 OBR — Part 2

## Overview

This guide continues the OBR discussion from Part 1 and focuses on the segments and workflow that surround an observation request in a real interface. It covers:

- the remaining OBR field definitions;
- `NTE` notes and comments;
- `ORC` order-control data;
- grouping multiple orders and results in one message;
- exporting orders to an external system;
- importing and reconciling returned results; and
- structured, narrative, PDF, and imaging result patterns.

The examples use HL7 v2 pipe-delimited syntax. Exact field requirements, codes, and optionality depend on the negotiated HL7 version and interface profile.

## Message Structure in Context

A typical result message is organized into a patient followed by one or more order/result groups:

```text
MSH
PID
[PV1]
{
  [ORC]
  OBR
  [NTE]
  {
    OBX
    [NTE]
  }
}
```

The braces mean “repeat.” An `OBR` identifies the requested service or report and acts as the parent for the related `OBX` observations. An `ORC`, when present, carries order-level control and workflow information. `NTE` adds human-readable comments to the segment immediately preceding it.

## NTE — Notes and Comments

`NTE` carries free-text or coded comments. Its meaning depends on placement:

- after `OBR`: a comment about the overall order or report;
- after `OBX`: a comment about that specific observation; and
- after another supported segment: a comment scoped to that segment.

### NTE fields

| Field | Name | Purpose |
|---|---|---|
| NTE-1 | Set ID - NTE | Sequence number for repeating NTE segments |
| NTE-2 | Source of Comment | Source, such as laboratory or ancillary system |
| NTE-3 | Comment | The narrative comment; may repeat |
| NTE-4 | Comment Type | Category of the comment |
| NTE-5 | Entered By | Person who entered the comment |
| NTE-6 | Entered Date/Time | When the comment was recorded |
| NTE-7 | Effective Start Date | When the comment becomes effective |
| NTE-8 | Expiration Date | When the comment stops being effective |

Example:

```hl7
OBR|1|ORD-1001|LAB-7788|87070^Bacterial Culture^CPT||||||||||||1234567890^PATEL^PRIYA|||||||||F
NTE|1|L|Moderate growth of Staphylococcus aureus|RE
OBX|1|CWE|ORG^Organism identified^L||3092008^Staphylococcus aureus^SCT||||||F
NTE|1|L|Methicillin-resistant isolate|RE
```

Here, the first note describes the report as a whole; the second note qualifies the organism observation.

### ORC and OBR must agree

When both segments contain an order identifier, keep the values consistent:

```hl7
ORC|RE|ORD-1001|LAB-7788|||||||||1234567890^PATEL^PRIYA
OBR|1|ORD-1001|LAB-7788|87070^Bacterial Culture^CPT||||||||||||1234567890^PATEL^PRIYA|||||||||F
```

- `ORC-2` should match `OBR-2` when both identify the same placer order.
- `ORC-3` should match `OBR-3` when both identify the same filler order.
- Provider values may appear in both segments, but field location and repetition must follow the interface agreement.

## Multiple Orders and Results

Do not flatten unrelated observations under one OBR. Repeat the order group instead:

```hl7
MSH|^~\&|LAB|FACILITY|EHR|CLINIC|20260927103000||ORU^R01|MSG-1001|P|2.5.1
PID|1||MRN-10001^^^FACILITY^MR||DOE^JANE||19850512|F
ORC|RE|ORD-1001|LAB-7788
OBR|1|ORD-1001|LAB-7788|87070^Bacterial Culture^CPT||||||||||||1234567890^PATEL^PRIYA|||||||||F
OBX|1|CWE|ORG^Organism identified^L||3092008^Staphylococcus aureus^SCT||||||F
NTE|1|L|Moderate growth|RE
ORC|RE|ORD-1002|LAB-7791
OBR|2|ORD-1002|LAB-7791|718-7^Hemoglobin^LN||||||||||||1234567890^PATEL^PRIYA|||||||||F
OBX|1|NM|718-7^Hemoglobin^LN||13.8|g/dL|12.0-16.0|N|||F
```

Notice that `OBR-1` increments across order groups, while `OBX-1` starts again within the second OBR group. Local profiles may impose different sequencing rules, so document the expected behavior.

## Outbound Order Export

The video reduces outbound processing to four practical stages:

1. **Pick** — select eligible orders that have not already been exported.
2. **Query** — retrieve the patient, encounter, order, provider, and destination data needed for the interface.
3. **Transform to HL7** — map source values into the agreed HL7 message structure and code systems.
4. **Send** — transmit the message and track its acknowledgement or delivery outcome.

A production implementation should also persist the message-control ID, destination, attempt count, send time, acknowledgement, and error detail. Idempotency is essential: retrying a failed transmission must not create a duplicate clinical order.

## Inbound Result Import

Inbound processing must identify the correct patient and order before filing results. The lesson highlights these matching dimensions:

- **Patient match** — commonly uses MRN and assigning authority; demographic values such as name, date of birth, or SSN may support reconciliation.
- **Order match** — commonly uses the placer order number in `OBR-2`/`ORC-2`, with the filler number in `OBR-3`/`ORC-3` as an additional key.
- **Provider match** — may use `OBR-16` and other provider fields defined by the local interface.

Matching rules are implementation policy, not universal HL7 rules. Avoid automatically filing on weak demographic similarity alone. Normalize identifiers and dates, require the appropriate assigning authority, and route ambiguous records for review.

### Reconciliation buckets

Use explicit queues so unmatched or questionable results are visible and recoverable:

| Bucket | Meaning | Recommended action |
|---|---|---|
| Matched | Patient and order match confidently | Validate and file the result |
| Patient unmatched | No safe patient match | Manual identity reconciliation |
| Order unmatched | Patient found, order not found | Search identifiers and order history |
| Provider unmatched | Ordering/copy provider cannot be resolved | Map provider or route to an authorized pool |
| Duplicate | Result/message already processed | Suppress duplicate and retain an audit record |
| Invalid | Parsing, vocabulary, or required-field error | Correct mapping or request retransmission |

## Common Result Representations

### 1. Structured ORU results

Discrete values are normally carried in `OBX` segments. Respect `OBX-2` when interpreting `OBX-5`:

```hl7
OBX|1|NM|718-7^Hemoglobin^LN||13.8|g/dL|12.0-16.0|N|||F
```

### 2. Narrative notes

Text can appear in `NTE` or in `OBX` with a text data type. Preserve repetition and line order; do not merge comments that have different clinical scopes.

### 3. PDF reports

A PDF may be embedded in `OBX-5`, usually with `OBX-2` set to `ED` and the document encoded as Base64:

```hl7
OBX|1|ED|REPORT^Clinical report^L||^application^pdf^Base64^JVBERi0xLjQK...||||||F
```

Before decoding or storing an attachment:

- validate the declared MIME type and encoding;
- enforce decoded-size limits;
- reject malformed or truncated Base64;
- scan according to the organization's security policy; and
- associate the document with the matched patient, order, and report status.

### 4. Imaging results

HL7 often carries the imaging order, report text, status, accession number, and links or identifiers used to find the study. The actual image objects are commonly exchanged through imaging standards and repositories rather than inserted directly into a normal ORU message. Follow the local radiology and DICOM integration profile.

## Validation Checklist

- Confirm the declared HL7 version and message profile.
- Parse using the delimiters declared in `MSH-1` and `MSH-2`.
- Preserve the `ORC` → `OBR` → `OBX`/`NTE` hierarchy.
- Confirm `ORC-2`/`ORC-3` and `OBR-2`/`OBR-3` agree where both are populated.
- Treat identifiers as composite values, including assigning authority where supplied.
- Validate patient, order, and provider matching independently.
- Honor result status in `OBR-25` and `OBX-11`; do not treat preliminary data as final.
- Keep NTE comments attached to the correct parent segment.
- Validate `OBX-2` before decoding `OBX-5`.
- Place unresolved results in reconciliation queues rather than silently dropping them.
- Make retries idempotent and retain an audit trail of exports, imports, acknowledgements, and corrections.
- Test multiple OBR groups, repeated OBX/NTE segments, corrections, cancellations, duplicates, and malformed attachments.

## Key Takeaways

1. `OBR` provides the clinical request/report context; `ORC` provides order-control context.
2. `NTE` meaning is determined by where the segment appears.
3. Every result must remain grouped beneath the correct OBR.
4. Reliable interfaces use strong patient and order identifiers plus visible reconciliation queues.
5. `OBX-5` can contain discrete data, text, or an encapsulated document; always interpret it using `OBX-2`.
6. Export and import pipelines require acknowledgement tracking, idempotency, validation, and auditability—not only message construction.
