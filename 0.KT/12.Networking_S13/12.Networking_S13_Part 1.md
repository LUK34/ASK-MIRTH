# HL7 Networking — Part 1

## Overview

This guide introduces the networking concepts commonly encountered when implementing and troubleshooting HL7 interfaces. It covers folder-based exchange, TCP/IP connectivity, network types, IP addresses, ports, firewalls, and the Windows commands used to diagnose connection problems.

> HL7 defines the structure and meaning of healthcare messages. The transport method—such as a shared folder or TCP connection—determines how those messages move between systems.

## Learning objectives

After completing this lesson, you should be able to:

- distinguish folder connectivity from TCP/IP connectivity;
- explain LAN, WAN, and VPN networking;
- describe the different roles of an IP address and a port;
- identify the sending client and receiving listener in an interface;
- use common Windows commands to investigate connectivity;
- recognize where firewall rules can block an HL7 connection; and
- troubleshoot an interface methodically, from the network layer through the HL7 acknowledgment.

## 1. Common connectivity methods

### Folder connectivity

With folder connectivity, one application writes files to a directory and another application reads them. The directory may be local or shared between servers.

A typical workflow is:

1. The source system creates an HL7 file.
2. The source places the file in an agreed directory.
3. The receiving integration engine monitors that directory.
4. The engine reads and processes the file.
5. The file is archived, moved, or marked as processed.

Both systems must agree on:

- the shared-folder path;
- the service account and its permissions;
- file naming and extension rules;
- character encoding;
- polling frequency;
- whether a file contains one message or multiple messages;
- how the writer signals that a file is complete; and
- archive, retry, duplicate, and error-handling rules.

To prevent a reader from opening a partially written file, the writer can create a temporary file and rename it only after writing is complete.

### TCP/IP connectivity

TCP/IP stands for **Transmission Control Protocol / Internet Protocol**. In a TCP interface, the sending application normally acts as the **client** and initiates a connection. The receiving application acts as the **server** and listens on an agreed port.

HL7 v2 messages are frequently exchanged over TCP using **Minimal Lower Layer Protocol (MLLP)**. MLLP adds framing characters so the receiver can determine where a message begins and ends. TCP connectivity alone does not guarantee that the message is correctly framed, valid, processed, or acknowledged.

## 2. Network types

| Network | Meaning | Typical use |
|---|---|---|
| LAN | Local Area Network | Connects devices within a limited location, such as a hospital or data center. |
| WAN | Wide Area Network | Connects LANs across larger distances through a carrier or service provider. |
| VPN | Virtual Private Network | Creates an encrypted tunnel across an untrusted or public network. |

A VPN can securely connect two organizational networks, but it does not automatically open every port. Routing, access-control lists, and host firewalls must still permit the required traffic.

## 3. IP addresses and ports

An **IP address** identifies a network interface or host. A **port** identifies the application service on that host.

Think of the IP address as the building address and the port as the particular door. A complete TCP destination requires both:

```text
Destination: 192.0.2.20:2575
```

The address above belongs to a documentation-only range. Replace it with the approved address and port for the relevant environment.

### Interface connection details

Record the following before configuring an interface:

| Item | Example |
|---|---|
| Environment | Test |
| Source system | EHR interface engine |
| Source IP | Approved source address |
| Destination system | Laboratory interface engine |
| Destination IP or FQDN | `192.0.2.20` |
| Destination port | `2575` |
| Transport | TCP with MLLP |
| Connection initiator | EHR |
| Listener | Laboratory system |
| Direction | Outbound from EHR; inbound to laboratory |
| Security | Private network, VPN, or TLS as agreed |
| Acknowledgment | Expected HL7 ACK behavior and timeout |

Avoid assuming that test and production use the same addresses, ports, credentials, or firewall rules.

## 4. Firewalls

A firewall permits or blocks network traffic according to rules. An interface may require:

- an outbound rule on the sending side;
- an inbound rule on the receiving side;
- permission for the exact protocol and destination port;
- restriction to approved source and destination IP addresses; and
- corresponding rules on intermediate network firewalls, VPNs, or cloud security controls.

Use least privilege: open only the required port, protocol, direction, and address range. A firewall change should follow the organization's approval and security process.

## 5. Windows diagnostic commands

Run these commands from the system whose network perspective you need to test. Results from your workstation do not necessarily represent what an interface server can reach.

### `ipconfig`

Displays the computer's IP configuration:

```powershell
ipconfig
ipconfig /all
```

Check the expected adapter, IP address, subnet mask, default gateway, and DNS configuration.

### `ping`

Tests whether a host responds to Internet Control Message Protocol (ICMP) echo requests:

```powershell
ping 192.0.2.20
```

Successful replies show that some network communication is possible. They do **not** prove that the HL7 TCP port is open. A failed ping also does not prove that the host is down, because ICMP may be blocked by policy.

### `netstat`

Displays active connections and listening ports:

```powershell
netstat -ano
netstat -ano | findstr :2575
```

Useful TCP states include:

| State | Meaning |
|---|---|
| `LISTENING` | A local process is waiting for inbound connections. |
| `ESTABLISHED` | A TCP connection is currently active. |
| `TIME_WAIT` | A recently closed connection is waiting before its resources are released. |

The `-o` option displays the process ID (PID), which can help identify the application owning a connection. Administrative privileges may be needed for further process inspection.

### `telnet`

Tests whether a TCP connection can be established to a host and port:

```powershell
telnet 192.0.2.20 2575
```

The Telnet Client feature may need to be enabled on Windows. A successful connection establishes that the TCP port accepted a connection; it does not prove that a valid MLLP-framed HL7 message will be accepted or that the receiver will return a valid ACK.

### PowerShell alternative

On modern Windows systems, `Test-NetConnection` provides clearer diagnostic output:

```powershell
Test-NetConnection 192.0.2.20 -Port 2575
```

Look at `TcpTestSucceeded`. If it is `False`, investigate the listener, routing, firewalls, VPN, and the accuracy of the address and port.

To inspect a local listener with PowerShell:

```powershell
Get-NetTCPConnection -LocalPort 2575
```

## 6. Recommended troubleshooting sequence

1. **Verify the configuration.** Confirm the environment, hostname or IP address, port, protocol, direction, and client/listener roles.
2. **Check the local network settings.** Use `ipconfig /all` and confirm that the expected network adapter and gateway are active.
3. **Check name resolution.** If a hostname is used, confirm that it resolves to the expected address.
4. **Check basic reachability.** Use `ping` when ICMP is permitted, while remembering its limitations.
5. **Check the receiver.** Confirm that the receiving application is running and listening on the configured port.
6. **Test the TCP port.** Use `Test-NetConnection` or `telnet` from the actual sending server.
7. **Inspect firewall and route controls.** Review host firewalls, network firewalls, VPN rules, network address translation, and cloud controls.
8. **Inspect active connections.** Use `netstat` to determine whether a listener or established session exists.
9. **Test the application protocol.** Send a correctly framed, non-production test message and inspect the receiver log and HL7 ACK.
10. **Review logs on both sides.** Correlate timestamps, connection attempts, message control IDs, retries, timeouts, and errors.

## 7. Interpreting common outcomes

| Observation | Likely interpretation | Next check |
|---|---|---|
| Ping succeeds; TCP test fails | Host is reachable, but the port is blocked, closed, or not listening. | Listener configuration and firewall rules |
| Ping fails; TCP test succeeds | ICMP is blocked, but the required TCP service is reachable. | Proceed with protocol-level testing |
| TCP test succeeds; no HL7 ACK | Network connection works, but framing, message content, application routing, or ACK configuration may be wrong. | MLLP settings and application logs |
| Port is listening locally; remote test fails | The service is active, but remote traffic may be blocked or routed incorrectly. | Bind address, host/network firewall, VPN, and NAT |
| Connection is established, then closes | The receiver may reject the protocol, framing, TLS mode, or idle behavior. | Logs on both systems and transport settings |
| Folder files are not processed | Path, permissions, file completion, naming, or polling may be incorrect. | Service account access and channel logs |

## 8. Security and operational guidance

- Do not place protected health information in an unsecured shared folder.
- Avoid sending unencrypted HL7 traffic across an untrusted network.
- Use an approved private network, VPN, or TLS arrangement where required.
- Restrict folder permissions and firewall rules to the necessary service accounts and hosts.
- Do not expose an HL7 listener directly to the public internet.
- Use synthetic or de-identified messages for connectivity testing.
- Never include patient data, credentials, or private infrastructure details in tickets or screenshots unless an approved secure channel is used.
- Monitor queues, retries, connection failures, and missing ACKs in production.

## 9. Implementation checklist

- [ ] Source and destination systems are identified.
- [ ] Client and listener roles are agreed.
- [ ] Test and production connection details are documented separately.
- [ ] Destination hostname/IP and port are confirmed.
- [ ] Transport and MLLP framing settings are agreed.
- [ ] VPN, routing, NAT, and firewall requirements are approved.
- [ ] The receiver is listening on the expected interface and port.
- [ ] Connectivity is tested from the actual sending server.
- [ ] Character encoding and message delimiters are agreed.
- [ ] ACK mode, timeout, and retry behavior are documented.
- [ ] A de-identified end-to-end message test succeeds.
- [ ] Monitoring, logging, archiving, and escalation procedures are in place.

## Key takeaway

Troubleshoot HL7 connectivity in layers. First verify the addressing and route, then the TCP port and listener, and finally MLLP framing, HL7 processing, and the acknowledgment. A successful test at one layer does not guarantee success at the next.
