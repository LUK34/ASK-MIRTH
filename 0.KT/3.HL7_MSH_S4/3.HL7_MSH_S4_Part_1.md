# HL7 Message Segments — MSH (Part 1)

> Beginner-friendly study notes and an experienced implementer's quick reference, prepared from **HL7_MSH_Part 1.mp4**.

## Learning objectives

By the end of this lesson, you should be able to:

- explain what an HL7 v2 message, segment, field, component, and subcomponent are;
- recognize the typical segments used in demographic ADT messages;
- explain why the **MSH (Message Header)** segment is mandatory;
- identify the purpose of the important MSH fields;
- read an MSH line without losing track of its field numbers;
- recognize common implementation and troubleshooting errors.

## 1. HL7 v2 messages in simple terms

HL7 v2 is a text-based format used by healthcare systems to exchange information. A message is made of ordered **segments**. Each segment normally occupies one line and begins with a three-character segment name.

```text
MSH|...
EVN|...
PID|...
PV1|...
```

Think of a message as an electronic envelope:

- **MSH** identifies the sender, receiver, message purpose, time, version, and message ID.
- The segments after MSH carry the clinical or administrative content.

### HL7 hierarchy

| Level | Meaning | Common delimiter |
|---|---|---:|
| Message | Complete transmission | Segment terminator, normally carriage return (`\r`) |
| Segment | One logical record, such as MSH or PID | Each segment begins on a new HL7 line |
| Field | A value inside a segment | `|` |
| Repetition | Multiple values in one field | `~` |
| Component | A part of a composite field | `^` |
| Subcomponent | A smaller part of a component | `&` |
| Escape sequence | Encoded delimiter or special data | `\` |

The standard encoding declaration is:

```text
|^~\&
```

Here, `|` is the field separator and `^~\&` declares the component, repetition, escape, and subcomponent characters.

## 2. Message types introduced in the lesson

The video introduces **ADT^A04** and **ADT^A28** as messages that carry patient demographic information.

- **ADT** means Admit, Discharge, Transfer—the broad administrative message family.
- **A04** is commonly used for registering a patient.
- **A28** is commonly used to add a person's demographic information.

The exact workflow meaning should always be agreed in the interface specification because organizations may use events differently.

### Segments shown for these messages

| Segment | Name | Main purpose |
|---|---|---|
| `MSH` | Message Header | Routing, identity, type, timestamp, version, and control information |
| `EVN` | Event Type | Details about the event and when it occurred |
| `PID` | Patient Identification | Patient identifiers and demographics |
| `PV1` | Patient Visit | Encounter, location, patient class, and provider information |
| `GT1` | Guarantor | Person or organization financially responsible |
| `IN1` | Insurance | Insurance-plan and coverage information |

Not every interface sends every optional segment. The agreed message profile determines what is required.

## 3. Why MSH is important

**MSH is the first and mandatory segment of an HL7 v2 message.** It contains the metadata that tells an interface engine or receiving application:

- which system sent the message;
- which system should receive it;
- when it was created;
- what kind of message it is;
- which unique control ID belongs to it;
- whether it is test or production data;
- which HL7 version and character encoding are in use.

If the MSH segment is malformed, the receiver may be unable to parse, route, validate, or acknowledge the entire message.

## 4. The MSH numbering rule that confuses beginners

Consider this beginning:

```text
MSH|^~\&|KNG_NUTRIO|KNG|MIRTH|SECA|...
```

MSH is special:

- the first character after `MSH` is **MSH-1**, the field separator (`|`);
- the next four characters form **MSH-2**, the encoding characters (`^~\&`);
- the next pipe-delimited value is therefore **MSH-3**, not MSH-2.

This special numbering applies to MSH because its first two fields define how the rest of the message must be parsed.

## 5. MSH field reference

The video displays the complete MSH definition and highlights the fields most often needed during interface implementation.

| Field | Standard name | Typical datatype | Requirement* | Practical meaning |
|---|---|---|---|---|
| `MSH-1` | Field Separator | ST | R | Normally `|` |
| `MSH-2` | Encoding Characters | ST | R | Normally `^~\&` |
| `MSH-3` | Sending Application | HD | O/profile-dependent | Name of the source application |
| `MSH-4` | Sending Facility | HD | O/profile-dependent | Organization/site that sent the message |
| `MSH-5` | Receiving Application | HD | O/profile-dependent | Destination application |
| `MSH-6` | Receiving Facility | HD | O/profile-dependent | Destination organization/site |
| `MSH-7` | Date/Time of Message | DTM/TS | R | Time the message was created |
| `MSH-8` | Security | ST | O | Legacy security information; often empty |
| `MSH-9` | Message Type | MSG | R | Message code, trigger event, and optionally structure |
| `MSH-10` | Message Control ID | ST | R | Unique identifier used for tracking and ACK correlation |
| `MSH-11` | Processing ID | PT | R | Usually `P`, `T`, or `D` |
| `MSH-12` | Version ID | VID | R | HL7 version, such as `2.5.1` |
| `MSH-13` | Sequence Number | NM | O | Optional message sequence |
| `MSH-14` | Continuation Pointer | ST | O | Used when a logical message is continued |
| `MSH-15` | Accept Acknowledgment Type | ID | O | Controls commit/accept acknowledgments |
| `MSH-16` | Application Acknowledgment Type | ID | O | Controls application-level acknowledgments |
| `MSH-17` | Country Code | ID | O | Country identifier |
| `MSH-18` | Character Set | ID | O/repeating | Character encoding, important for Arabic and other non-ASCII text |
| `MSH-19` | Principal Language of Message | CWE/CE | O | Main language of the message |
| `MSH-20` | Alternate Character Set Handling Scheme | ID | O | How alternate character sets are handled |
| `MSH-21` | Message Profile Identifier | EI | O/repeating | Identifies the conformance profile governing the message |

\* `R` means required and `O` means optional in the base definition shown. A local implementation profile may make additional fields mandatory. Datatype names vary slightly by HL7 v2 version; use the exact version declared in MSH-12.

## 6. Important fields explained

### MSH-3 to MSH-6 — sender and receiver

These fields describe the route:

```text
MSH-3  Sending Application
MSH-4  Sending Facility
MSH-5  Receiving Application
MSH-6  Receiving Facility
```

They are often used by Mirth Connect to select a channel, route a message, populate metadata, or reject an unexpected source. Use stable system identifiers rather than informal display names.

### MSH-7 — message timestamp

A common value is:

```text
20260921223045+0300
```

This means `2026-09-21 22:30:45` with a `+03:00` UTC offset. HL7 timestamps can use different precision, but sender and receiver must agree on the expected format and timezone policy.

### MSH-9 — message type

MSH-9 is composite. A common value is:

```text
ADT^A28^ADT_A05
```

| Component | Example | Meaning |
|---|---|---|
| `MSH-9.1` | `ADT` | Message code/family |
| `MSH-9.2` | `A28` | Trigger event |
| `MSH-9.3` | `ADT_A05` | Abstract message structure |

Do not treat `ADT`, `A28`, and `ADT_A05` as three separate fields; they are components of MSH-9.

### MSH-10 — message control ID

The control ID should uniquely identify a message within the parties' agreed retention window. It is normally returned in the acknowledgment's `MSA-2` field.

```text
Incoming: MSH-10 = KNG-20260921-000001
ACK:      MSA-2  = KNG-20260921-000001
```

This correlation is essential for audit logs, retries, duplicate detection, and troubleshooting.

### MSH-11 — processing ID

Common values are:

| Value | Meaning |
|---|---|
| `P` | Production |
| `T` | Training |
| `D` | Debugging |

Never allow a test message to update production data merely because it reached a production endpoint. Validate MSH-11 as part of the receiving workflow.

### MSH-12 — HL7 version

Examples include `2.3`, `2.4`, `2.5`, and `2.5.1`. The version affects field definitions, data types, message structures, and validation rules. Configure the parser for the declared and contractually supported version.

### MSH-15 and MSH-16 — acknowledgment behavior

Common control values include:

- `AL` — always;
- `NE` — never;
- `ER` — only on error/reject;
- `SU` — only on successful completion.

The two fields address different acknowledgment stages. MSH-15 concerns accept/commit acknowledgment, while MSH-16 concerns application acknowledgment. Many real interfaces simplify this behavior, so document the actual agreement instead of assuming it.

### MSH-18 — character set

For messages containing Arabic patient names, character-set agreement is critical. A mismatch can produce question marks or corrupted characters even when the original database value is correct. Use UTF-8 end-to-end when supported and ensure the declared MSH-18 value matches the bytes actually transmitted.

## 7. Fully worked example

```hl7
MSH|^~\&|KNG_NUTRIO|KNG_HQ|MIRTH|SECA|20260921223045+0300||ADT^A28^ADT_A05|KNG-20260921-000001|P|2.5.1|||AL|AL|KWT|UNICODE UTF-8|ARA
EVN|A28|20260921223045+0300
PID|1||51006^^^KNG^MR||TEST PATIENT^ONE||19880625|F
```

### Parse of the MSH line

| Location | Value | Interpretation |
|---|---|---|
| MSH-1 | `|` | Field separator |
| MSH-2 | `^~\&` | Encoding characters |
| MSH-3 | `KNG_NUTRIO` | Sending application |
| MSH-4 | `KNG_HQ` | Sending facility |
| MSH-5 | `MIRTH` | Receiving application/interface engine |
| MSH-6 | `SECA` | Receiving facility/system |
| MSH-7 | `20260921223045+0300` | Message creation time |
| MSH-8 | empty | No security value supplied |
| MSH-9 | `ADT^A28^ADT_A05` | Demographic add-person event |
| MSH-10 | `KNG-20260921-000001` | Unique message control ID |
| MSH-11 | `P` | Production processing |
| MSH-12 | `2.5.1` | HL7 version |
| MSH-13/14 | empty | Sequence and continuation not used |
| MSH-15/16 | `AL` / `AL` | Always request acknowledgment |
| MSH-17 | `KWT` | Country code |
| MSH-18 | `UNICODE UTF-8` | Character set |
| MSH-19 | `ARA` | Principal language is Arabic |

> The example is illustrative. Confirm country, language, character-set coding, and profile rules with the receiving system before production use.

## 8. How to read an HL7 definition table

The field-definition table in the lesson contains columns similar to these:

| Column | Meaning |
|---|---|
| SEQ | Field position, such as MSH-9 |
| LENGTH | Maximum length defined by that version/profile |
| DT | HL7 datatype, such as ST, HD, DTM, MSG, PT, or VID |
| OPT | Optionality: commonly `R` required, `O` optional, or profile-specific conditions |
| RPT/# | Whether the field may repeat and, sometimes, its repetition limit |
| TBL# | HL7 table associated with coded values |
| NAME | Human-readable field name |

Base-standard optionality is not the final word. A hospital, device vendor, national program, or interface profile can constrain the standard and require specific optional fields.

## 9. Common mistakes

1. **Counting MSH fields like other segments.** Remember that `|` itself is MSH-1 and `^~\&` is MSH-2.
2. **Sending a non-unique MSH-10.** This breaks ACK correlation and can trigger duplicate-processing rules.
3. **Confusing the trigger event with the structure.** In `ADT^A28^ADT_A05`, `A28` is the trigger; `ADT_A05` is the structure.
4. **Hard-coding production mode.** Validate MSH-11 and separate test/training traffic appropriately.
5. **Ignoring the declared HL7 version.** A parser configured for the wrong version may silently map fields incorrectly.
6. **Using line-feed-only segment endings without agreement.** Traditional HL7 v2 uses carriage return (`\r`) as the segment terminator.
7. **Declaring UTF-8 but transmitting another encoding.** The declaration and actual byte encoding must match.
8. **Assuming optional means unnecessary.** A receiving system's conformance profile may require it.
9. **Logging confidential content carelessly.** Protect patient identifiers and clinical data in logs.
10. **Retrying without an idempotency strategy.** Decide whether a retry retains the original control ID and how duplicates are handled.

## 10. Mirth Connect implementation checklist

Before accepting or sending a message, verify:

- [ ] MSH is present and is the first segment.
- [ ] MSH-1 and MSH-2 contain the agreed delimiters.
- [ ] MSH-3 through MSH-6 identify approved endpoints.
- [ ] MSH-7 is parseable and follows the timezone policy.
- [ ] MSH-9 contains an allowed message code, event, and structure.
- [ ] MSH-10 is present, logged securely, and usable for ACK correlation.
- [ ] MSH-11 matches the environment.
- [ ] MSH-12 is supported by the channel/parser.
- [ ] MSH-15/MSH-16 behavior matches the ACK design.
- [ ] MSH-18 matches the actual byte encoding.
- [ ] Required downstream segments are present for the selected event.
- [ ] Validation failure produces a controlled ACK/rejection and useful audit entry.

### Useful Mirth field access examples

In a JavaScript transformer, fields are commonly accessed from the parsed message tree:

```javascript
var sendingApplication = msg['MSH']['MSH.3']['MSH.3.1'].toString();
var messageCode        = msg['MSH']['MSH.9']['MSH.9.1'].toString();
var triggerEvent       = msg['MSH']['MSH.9']['MSH.9.2'].toString();
var controlId          = msg['MSH']['MSH.10']['MSH.10.1'].toString();
var processingId       = msg['MSH']['MSH.11']['MSH.11.1'].toString();
var versionId          = msg['MSH']['MSH.12']['MSH.12.1'].toString();
```

Example validation:

```javascript
if (messageCode !== 'ADT' || triggerEvent !== 'A28') {
    throw 'Unsupported message type: ' + messageCode + '^' + triggerEvent;
}

if (processingId !== 'P') {
    throw 'Unexpected processing ID: ' + processingId;
}
```

Adapt field access and error handling to the Mirth Connect version and the channel's inbound datatype settings.

## 11. Quick revision sheet

- **MSH** = mandatory Message Header and first segment.
- **MSH-1** = field separator, normally `|`.
- **MSH-2** = encoding characters, normally `^~\&`.
- **MSH-3/4** = sender application/facility.
- **MSH-5/6** = receiver application/facility.
- **MSH-7** = message creation timestamp.
- **MSH-9** = message code + trigger event + optional structure.
- **MSH-10** = unique control ID; ACK normally echoes it in MSA-2.
- **MSH-11** = processing mode (`P`, `T`, or `D`).
- **MSH-12** = HL7 version.
- **MSH-15/16** = acknowledgment preferences.
- **MSH-18** = character set—especially important for Arabic data.

## 12. Knowledge check

1. Why is MSH-1 different from the first field in most other segments?
2. What are the three components of `ADT^A28^ADT_A05`?
3. Which field links an incoming message to its acknowledgment?
4. Which fields identify the source and destination systems?
5. Why should MSH-11 be validated in production?
6. What can happen if MSH-18 says UTF-8 but the transmitted bytes use another encoding?

### Answers

1. MSH-1 is the delimiter character itself; it defines how the rest of the message is separated.
2. Message code `ADT`, trigger event `A28`, and message structure `ADT_A05`.
3. MSH-10, normally echoed in MSA-2.
4. MSH-3 through MSH-6.
5. To prevent training/debug messages from being processed as genuine production transactions.
6. Non-ASCII content—such as Arabic names—may become corrupted or unreadable.
