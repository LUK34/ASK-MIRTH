# HL7 PID Segment — Part 1

> Beginner-friendly study notes and practical implementation guidance prepared from **2.PID Part 1.mp4**.

## Learning objectives

After studying this lesson, you should be able to:

- explain the purpose of the PID segment;
- recognize the PID fields displayed in the HL7 definition table;
- understand why `PID-3` is a repeating field;
- separate multiple patient identifiers using the repetition delimiter `~`;
- distinguish a field repetition from a component separated by `^`;
- identify the purpose of assigning-authority information in a CX identifier;
- interpret the standard values shown for `PID-8` Administrative Sex;
- extract and validate PID values in Mirth Connect;
- avoid common patient-identity mapping mistakes.

## 1. What is the PID segment?

**PID** means **Patient Identification**. It contains information used to identify a patient record.

A PID segment can carry:

- patient identifiers;
- patient name;
- mother's maiden name;
- date of birth;
- administrative sex;
- race and ethnicity;
- address;
- telephone or telecommunications information;
- language, marital status, and religion;
- account and other legacy identification details;
- birth-related information.

Example:

```hl7
PID|1||9541236254~81698786^^^MRN~0008169^^^SYSID||TEST^PATIENT^A|TESTMOTHER|20150104|M
```

The lesson uses a similar dummy PID line to explain how multiple patient identifiers can be carried in `PID-3`.

## 2. Position of PID in an ADT message

The training material places PID inside an ADT demographic message such as ADT^A04 or ADT^A28.

```hl7
MSH|^~\&|SENDING_APP|SENDING_FACILITY|RECEIVING_APP|RECEIVING_FACILITY|20260922100000||ADT^A28|MSG000001|T|2.5.1
EVN|A28|20260922100000
PID|1||9541236254~81698786^^^MRN~0008169^^^SYSID||TEST^PATIENT^A|TESTMOTHER|20150104|M
```

| Segment | Purpose |
|---|---|
| `MSH` | Message header and routing information |
| `EVN` | Event information |
| `PID` | Patient identifiers and demographics |

Other segments such as PV1, GT1, and IN1 may follow, depending on the event and the agreed message profile.

## 3. HL7 delimiters used in the example

The message header normally declares:

```text
MSH|^~\&
```

| Symbol | Name | Meaning |
|---:|---|---|
| `|` | Field separator | Separates PID-1, PID-2, PID-3, and other fields |
| `^` | Component separator | Separates parts inside a composite value |
| `~` | Repetition separator | Separates multiple occurrences of the same field |
| `\` | Escape character | Begins and ends HL7 escape sequences |
| `&` | Subcomponent separator | Separates smaller parts inside a component |

The main demonstration in this video concerns `~` and `^` inside PID-3.

## 4. How to count PID fields

Unlike MSH, PID field counting follows the ordinary rule: count pipe-separated values after the segment name.

```hl7
PID|1||9541236254~81698786^^^MRN~0008169^^^SYSID||TEST^PATIENT^A|TESTMOTHER|20150104|M
    │ │ └────────────────────────────────────────┘  └──────────────┘ └────────┘ └──────┘ │
    │ │                  PID-3                         PID-5          PID-6     PID-7  PID-8
    │ PID-2 is empty
    PID-1
```

Important observations:

- `PID-1` contains `1`.
- `PID-2` is empty, so two pipe characters appear together after PID-1.
- `PID-3` contains three repeated identifiers.
- `PID-4` is empty.
- `PID-5` contains the patient name.

Empty fields still occupy their positions. Do not remove empty delimiters when manually reading or constructing a message.

### Understanding the definition-table columns

| Column | Meaning |
|---|---|
| `SEQ` | Field position, such as PID-3 |
| `LENGTH` | Length specified by the selected HL7 version/profile |
| `DT` | HL7 datatype |
| `OPT` | Optionality or compatibility status |
| `RPT/#` | Whether the field repeats and its repetition limit |
| `TBL#` | Associated HL7 table |
| `NAME` | Standard field name |

The displayed table uses indicators including:

- `R` — required;
- `O` — optional;
- `W` — withdrawn;
- `B` — retained for backward compatibility;
- `*` in the repetition column — repetition is allowed, with constraints determined by the definition or profile.

Requirements can vary by HL7 version and local implementation profile. Always check MSH-12 and the agreed interface specification.

## 6. PID-3 — Patient Identifier List

PID-3 is the main focus of the practical demonstration.

### Why PID-3 repeats

One patient may have several identifiers, for example:

- civil ID;
- military number;
- medical record number (MRN);
- hospital patient ID;
- legacy-system ID;
- device or external-system ID.

HL7 does not require all of these to be concatenated into one identifier. PID-3 repeats, and the repetitions are separated with `~`.

### Example shown in the lesson

The video separates PID-3 into three repetitions similar to these:

```text
PID-3 repetition 1 = 9541236254
PID-3 repetition 2 = 81698786^^^MRN
PID-3 repetition 3 = 0008169^^^SYSID
```

Combined inside the HL7 field:

```hl7
9541236254~81698786^^^MRN~0008169^^^SYSID
```

The repetition delimiter is `~`:

```text
9541236254  ~  81698786^^^MRN  ~  0008169^^^SYSID
     #1                 #2                  #3
```

### `~` versus `^`

- `~` starts another occurrence of PID-3.
- `^` moves to another component inside the current PID-3 occurrence.

Therefore:

```text
81698786^^^MRN
```

is one CX value, not four field repetitions.

## 7. Understanding the CX datatype

PID-3 uses the **CX — Extended Composite ID with Check Digit** datatype.

A commonly encountered CX structure is:

```text
ID Number ^ Check Digit ^ Check Digit Scheme ^ Assigning Authority ^ Identifier Type Code ^ Assigning Facility ^ ...
```

| Component | Common meaning |
|---|---|
| `CX.1` | ID number |
| `CX.2` | Check digit |
| `CX.3` | Check-digit scheme |
| `CX.4` | Assigning authority |
| `CX.5` | Identifier type code |
| `CX.6` | Assigning facility |

The exact component definition must be checked against the declared HL7 version.

### Interpreting consecutive carets

```text
81698786^^^MRN
```

Conceptually:

| Component | Value |
|---|---|
| CX.1 | `81698786` |
| CX.2 | empty |
| CX.3 | empty |
| CX.4 | `MRN` |

Three consecutive carets do not mean “three unknown values.” They preserve the positions of the empty CX.2 and CX.3 components before CX.4.

### Important modelling note

In the literal value `81698786^^^MRN`, `MRN` occupies CX.4, the assigning-authority position. If the intention is to state that the identifier type is a medical record number, a profile may instead use a structure such as:

```text
81698786^^^APOLLO^MR
```

Here:

- `APOLLO` is the assigning authority in CX.4;
- `MR` is the identifier type in CX.5.

The sender and receiver must agree on the exact CX mapping. Do not infer the meaning of a component merely from its text.

## 8. Safe identifier selection

The following approach is unsafe:

```javascript
var patientId = msg['PID']['PID.3']['PID.3.1'].toString();
```

It may return only the first repetition, even when the required MRN or military number appears later.

A safer strategy is:

1. Inspect every PID-3 repetition.
2. Read the ID number.
3. Read the assigning authority.
4. Read the identifier type.
5. Select the repetition matching the interface contract.
6. Reject or quarantine ambiguous data rather than guessing.

Conceptual Mirth JavaScript:

```javascript
var selectedId = '';

for each (var cx in msg['PID']['PID.3']) {
    var idNumber = cx['PID.3.1'].toString();
    var assigningAuthority = cx['PID.3.4'].toString();
    var identifierType = cx['PID.3.5'].toString();

    if (assigningAuthority === 'KNG' && identifierType === 'MR') {
        selectedId = idNumber;
        break;
    }
}

if (!selectedId) {
    throw 'Required KNG medical record number was not found in PID-3';
}
```

Mirth's exact XML representation can vary with the inbound datatype and serializer version. Confirm the iteration against an actual transformed message in your channel.

## 9. PID-5 — Patient Name

PID-5 uses the XPN datatype and may repeat.

Simplified example:

```hl7
TEST^PATIENT^A
```

Typical components include:

| Component | Meaning |
|---|---|
| XPN.1 | Family name |
| XPN.2 | Given name |
| XPN.3 | Second/additional given names |
| XPN.4 | Suffix |
| XPN.5 | Prefix |

Do not place the complete name into one component unless the interface specification explicitly requires it.

For English and Arabic patient names:

- agree whether PID-5 will repeat for different representations;
- use the agreed name-type and representation components where supported;
- transmit the bytes using the character set declared in MSH-18;
- preserve the original name and avoid uncontrolled transliteration.

## 10. PID-7 — Date/Time of Birth

The lesson's example shows a value similar to:

```text
20150104
```

This represents:

```text
2015-01-04
```

HL7 date/time values use decreasing precision. Do not invent a day, month, time, or timezone that the sending system did not provide.

Basic Mirth access:

```javascript
var dateOfBirth = msg['PID']['PID.7']['PID.7.1'].toString();
```

## 11. PID-8 — Administrative Sex

The lesson opens HL7 table **0001 — Administrative Sex** for HL7 v2.5.1.

The values shown are:

| Code | Description |
|---|---|
| `A` | Ambiguous |
| `F` | Female |
| `M` | Male |
| `N` | Not applicable |
| `O` | Other |
| `U` | Unknown |

The example PID segment uses:

```text
PID-8 = M
```

which maps to **Male** in the displayed table.

### Important distinction

PID-8 is named **Administrative Sex**. Do not automatically treat it as equivalent to every other concept involving sex or gender. A modern system may maintain separate concepts based on jurisdiction, clinical requirements, and the applicable interoperability standard.

### Unknown is not the same as empty

- `U` means the sender explicitly reports the value as unknown.
- An empty PID-8 means no value was supplied.

Do not silently convert an empty value into `M`, `F`, or another assumed value.

## 12. Other important PID fields

### PID-11 — Patient Address

PID-11 uses XAD and may repeat for home, mailing, temporary, or other address types.

### PID-13 and PID-14 — Telecommunications

These use XTN and may carry telephone, email, or other telecommunications information depending on the HL7 version and profile.

### PID-15 — Primary Language

This is a coded field. For Arabic or English, use codes agreed with the receiving system rather than arbitrary display text.

### PID-18 — Patient Account Number

This normally identifies a patient account. It must not be confused with the patient identifier in PID-3 or an encounter number in PV1.

### PID-24 — Multiple Birth Indicator

This identifies whether the patient was part of a multiple birth. It is not the birth order; later PID fields in applicable versions can carry birth-order information.


### PID-3 interpretation

| Repetition | Identifier | Assigning authority | Type | Intended meaning |
|---|---:|---|---|---|
| 1 | `9541236254` | `CIVIL` | `NNKWT` | Illustrative civil identifier |
| 2 | `81698786` | `KNG` | `MR` | Illustrative KNG medical record number |
| 3 | `0008169` | `LEGACY` | `PI` | Illustrative legacy patient identifier |

All values are fictional and intended only for training. Confirm identifier-type codes and authority naming with the receiving system.

## 14. Mirth Connect extraction examples

```javascript
var setId = msg['PID']['PID.1']['PID.1.1'].toString();
var familyName = msg['PID']['PID.5']['PID.5.1'].toString();
var givenName = msg['PID']['PID.5']['PID.5.2'].toString();
var dateOfBirth = msg['PID']['PID.7']['PID.7.1'].toString();
var administrativeSex = msg['PID']['PID.8']['PID.8.1'].toString();
```

### PID-8 validation example

```javascript
var administrativeSex = msg['PID']['PID.8']['PID.8.1'].toString();
var allowedSexCodes = ['A', 'F', 'M', 'N', 'O', 'U'];

if (administrativeSex && allowedSexCodes.indexOf(administrativeSex) === -1) {
    throw 'Unsupported PID-8 Administrative Sex code: ' + administrativeSex;
}
```

This example permits an empty field. Whether PID-8 is required depends on the interface profile.

## 15. Patient-identity validation checklist

- [ ] PID is present when required by the message structure.
- [ ] PID-3 contains at least one acceptable patient identifier.
- [ ] Every selected identifier includes the agreed authority and type information.
- [ ] All PID-3 repetitions are inspected before selecting an identifier.
- [ ] Duplicate identifiers do not contradict each other.
- [ ] Withdrawn fields such as PID-2 or PID-4 are not used for new mappings unless compatibility requires them.
- [ ] PID-5 name components are mapped correctly.
- [ ] PID-7 follows the agreed precision and date format.
- [ ] PID-8 is validated against the correct code table/profile.
- [ ] Missing and explicitly unknown values remain distinguishable.
- [ ] Character encoding supports Arabic and English names correctly.
- [ ] Full PID data is not written to unsecured application logs.
- [ ] Ambiguous identity matches are quarantined or rejected instead of guessed.

## 16. Common mistakes

1. **Treating `~` and `^` as the same delimiter.** `~` creates another field repetition; `^` creates another component.
2. **Reading only the first PID-3 repetition.** The required identifier may be the second or third.
3. **Comparing identifier numbers without their authority.** The same number can exist in different namespaces.
4. **Calling CX.4 the identifier type.** CX.4 is normally the assigning authority; CX.5 normally carries the type code.
5. **Removing empty fields.** This shifts every following PID value into the wrong position.
6. **Using withdrawn PID fields for a new interface.** Prefer the current version-appropriate field.
7. **Hard-coding `M` and `F` as the only PID-8 values.** The displayed table includes `A`, `N`, `O`, and `U` as well.
8. **Treating empty PID-8 as `U`.** Empty and explicitly unknown carry different information.
9. **Using a patient account number as a patient identifier.** PID-18 and PID-3 serve different purposes.
10. **Logging the entire PID segment.** It may expose sensitive personal information.
