# HL7 Import and Export — Part 2

## Overview

This guide continues the HL7 import/export workflow from Part 1, with emphasis on importing scheduling messages into an EHR or practice-management system. It explains how to validate an inbound message, identify the patient and appointment, interpret the appointment status in `SCH-25`, and verify that the target scheduling application reflects the intended result.

The central lesson is that receiving a syntactically valid HL7 message is only the beginning. A safe import must correlate that message with the correct local records and apply an idempotent business action.

## Learning objectives

After completing this part, you should be able to:

- distinguish the export and import responsibilities;
- validate an inbound scheduling message before processing it;
- match the patient and appointment to local records;
- use `SCH-25` to drive appointment-state changes;
- understand where AIG resource data fits into scheduling messages;
- test the workflow in both the interface engine and the destination application.

## End-to-end workflow

### Export: practice-management system to EHR

1. Identify the data that must be sent.
2. Query the source database.
3. Transform the query result into the agreed HL7 SIU structure.
4. Send the message to the receiving EHR or interface engine.

The outbound transformation should populate the exact segments and fields required by the interface specification. Do not assume that a value shown in the source UI has the same code or format expected by the receiver.

### Import: HL7 message to EHR

1. Parse the message using the delimiters declared in `MSH`.
2. Validate the message type, version, required segments, and required fields.
3. Check whether the message or business event has already been processed.
4. Identify the patient using approved identifiers.
5. Identify the appointment using the agreed appointment identifier.
6. Read the requested appointment state, particularly `SCH-25` when that is the agreed status field.
7. Apply the corresponding insert or update in a controlled transaction.
8. Return an appropriate acknowledgment and record an audit trail.

## Validation before import

Validation should happen before any database change.

### Envelope checks

- Confirm that `MSH` is present and readable.
- Confirm the expected sending and receiving applications/facilities.
- Confirm the supported HL7 version.
- Confirm the expected message type and trigger event, such as an SIU scheduling event.
- Require a unique message control ID (`MSH-10`).

### Structural checks

- Verify that mandatory segments are present.
- Reject or quarantine malformed segments and unexpected repetitions.
- Validate field types, date/time formats, code values, and field lengths.
- Enforce the receiver-specific conformance profile, not only the base HL7 grammar.

### Business checks

- Ensure the patient can be matched unambiguously.
- Ensure an update or cancellation identifies an existing appointment.
- Confirm that the requested state transition is allowed.
- Confirm that referenced resources exist when resource matching is required.

## Patient and appointment correlation

### Patient matching

Use a stable enterprise or facility identifier whenever possible. In many interfaces this is carried in `PID-3` (Patient Identifier List), including the assigning authority and identifier type.

Avoid matching solely on demographic values such as name or date of birth. If a secondary match is permitted, require enough attributes to make the result unambiguous and route uncertain matches to an exception queue.

### Appointment matching

The video highlights the appointment identifier in `SCH-1`. In the HL7 SIU model, `SCH-1` is commonly the placer appointment ID and `SCH-2` the filler appointment ID. The actual interface agreement must define which identifier is authoritative.

Recommended local correlation record:

| Value | Purpose |
|---|---|
| Sending application/facility | Namespaces the external identifier |
| `SCH-1` | Placer appointment identifier |
| `SCH-2` | Filler appointment identifier, when supplied |
| Local appointment ID | Target-system primary key |
| `MSH-10` | Message-level duplicate detection |
| Last accepted event/status | Guards against stale or repeated updates |

Never treat `MSH-10` as the appointment ID: it identifies a message instance, not the underlying appointment.

## Appointment status in `SCH-25`

The lesson uses `SCH-25` to represent the appointment's status. Examples discussed include:

- booked;
- checked in or acknowledged;
- cancelled;
- rescheduled;
- bumped.

These labels should be treated as interface-specific examples rather than universal literal values. HL7 versions and implementation guides may use coded values, local values, or a different field to express workflow state. Build a configurable mapping agreed by sender and receiver.

| Incoming meaning | Typical local action | Important rule |
|---|---|---|
| Booked | Create or confirm the appointment | Do not create a duplicate when the appointment already exists |
| Checked in / acknowledged | Advance the visit workflow | Require an existing appointment and an allowed transition |
| Cancelled | Mark the appointment cancelled | Preserve the appointment and audit history unless policy says otherwise |
| Rescheduled | Update the appointment time or link old/new appointments | Define whether the sender reuses the same ID |
| Bumped | Record provider/system-initiated displacement | Do not silently translate it to patient cancellation |

### Suggested status-processing logic

```text
status = normalize(SCH-25)

if status is unsupported:
    quarantine message and return the configured error acknowledgment
else if appointment does not exist and status is not a create/book action:
    raise a business-validation exception
else if event was already applied:
    acknowledge without applying it again
else:
    validate transition
    apply mapped business action
    record message ID, appointment ID, old status, and new status
```

## AIG: appointment resource information

The final portion of the lesson refers to the `AIG` (Appointment Information — General Resource) segment. It can describe a general resource assigned to an appointment.

Fields shown in the reference include:

| Field | Meaning |
|---|---|
| `AIG-1` | Set ID |
| `AIG-2` | Segment action code |
| `AIG-3` | Resource ID |
| `AIG-4` | Resource type |
| `AIG-5` | Resource group |
| `AIG-6` | Resource quantity |
| `AIG-7` | Resource quantity units |
| `AIG-8` | Start date/time |
| `AIG-9` | Start date/time offset |
| `AIG-10` | Offset units |
| `AIG-11` | Duration |
| `AIG-12` | Duration units |
| `AIG-13` | Allow substitution code |
| `AIG-14` | Filler status code |

The demonstrated sample associates an appointment with a general resource and also shows a separate `AIL` line for location information. Keep the resource concepts distinct:

- `AIP`: personnel resource;
- `AIG`: general resource;
- `AIL`: location resource.

Do not use AIG as a substitute for patient, provider, or location matching. Resource identifiers must be mapped to valid target-system records, preferably using a maintained crosswalk.

## Example message fragment

The following is an illustrative fragment, not a verbatim transcript of the demonstration. The exact event code, identifiers, repetitions, and status codes must follow the project specification.

```hl7
MSH|^~\\&|SCHEDULER|GENERAL_HOSPITAL|EHR|GENERAL_HOSPITAL|20260925103000||SIU^S12|MSG000372|P|2.5
PID|1||1000000641^^^MRN^MR||Schedule^Singh||19800101|M
SCH|372|||||||FOLLOW-UP^Follow-up visit|||||||||12345^Ames^Joan||||||||BOOKED
PV1|1|O|||||56789^Samuel^Christopher|||||||||||||||||||||||||||||||||||||||||20260925110000
AIG|1|A|68^Exam table 2|RESOURCE|||||20260925110000|||30|min
AIL|1|A|25^Atlanta Clinic|ROOM||||20260925110000|||30|min
```

Key interpretation:

- `MSH-10` identifies this message for acknowledgment and duplicate-message handling.
- `PID-3` identifies the patient in the agreed namespace.
- `SCH-1` identifies the appointment for correlation.
- `SCH-25` carries the status only if the trading-partner specification defines it that way.
- `AIG` and `AIL` describe assigned resources and location.

## Idempotency and event ordering

Duplicate protection must operate at two levels:

1. **Message level:** detect a repeated `MSH-10` from the same sender.
2. **Business level:** prevent a repeated event with a new control ID from creating another appointment or reapplying the same status.

Out-of-order events require an explicit policy. For example, an old “booked” event arriving after a newer cancellation must not reopen the appointment automatically. Store event timestamps and the last accepted state, and quarantine ambiguous cases for review.

## Acknowledgments and errors

Return acknowledgments according to the interface contract:

- `AA`: message accepted;
- `AE`: message parsed but contains an application-level error;
- `AR`: message rejected, for example because it cannot be parsed or routed.

An acknowledgment should contain the original message control ID and enough error detail to support remediation without exposing unnecessary patient data.

## Testing checklist

### Happy-path tests

- A new booked appointment is created once.
- An existing appointment advances to checked-in/acknowledged.
- A cancellation updates the intended appointment.
- A reschedule changes the intended time and resources.
- Valid AIG and AIL identifiers map to the correct target records.

### Negative tests

- Missing `MSH`, `PID`, or `SCH`.
- Missing or unknown patient identifier.
- Unknown appointment ID on an update.
- Unsupported `SCH-25` value.
- Invalid date/time or duration.
- Unknown AIG resource identifier.
- Illegal transition, such as applying an older booked event after cancellation.

### Reliability tests

- Replay the exact same `MSH-10`.
- Send the same business event with a different `MSH-10`.
- Deliver events out of order.
- Simulate a database failure during the transaction.
- Confirm that retrying after a timeout does not duplicate the appointment.

### UI verification

The destination application's appointment screen is useful for confirming visible outcomes, but it is not the only source of truth. Verify all three layers:

1. interface-engine processing and acknowledgment;
2. database or application audit record;
3. visible appointment status, time, provider, location, and resource assignment.

## Operational checklist

- Maintain a version-controlled field mapping and status crosswalk.
- Log message control ID, patient correlation result, appointment correlation result, and state transition.
- Mask protected health information in routine logs.
- Use an exception queue for unmatched or ambiguous records.
- Monitor rejection rate, duplicate rate, processing latency, and retry volume.
- Reconcile source and target appointments periodically.
- Document retry, replay, and manual-correction procedures.

## Common mistakes

- Confusing a message control ID with an appointment ID.
- Creating a new appointment for every inbound event.
- Hard-coding display text instead of mapping coded statuses.
- Matching patients only by name.
- Assuming every sender uses identical `SCH-25` values.
- Deleting cancelled appointments and losing audit history.
- Accepting a syntactically valid message without validating the business transition.
- Returning `AA` before the durable business transaction has completed when the contract expects application acknowledgment.

## Summary

A dependable scheduling import is a correlation and state-management workflow, not merely an HL7 parser. Validate first, match the patient and appointment with stable identifiers, map `SCH-25` through an agreed code table, process events idempotently, and verify the result in both the integration layer and the scheduling application. Use AIG, AIP, and AIL only for their intended resource roles and maintain explicit crosswalks to the target system.
