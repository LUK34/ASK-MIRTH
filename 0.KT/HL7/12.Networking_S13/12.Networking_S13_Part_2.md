# HL7 Networking — Part 2

## Overview

This guide continues the networking foundations used in HL7 interface implementations. It covers connectivity testing, firewall behavior, FTP/SFTP file exchange, SOAP and REST web services, database connectivity, and a supplementary SmartHL7 Viewer configuration demonstration.

The central troubleshooting principle is simple: verify each layer separately. A reachable server, an open TCP port, and a successfully processed HL7 message are three different outcomes.

## Learning objectives

After completing this lesson, you should be able to:

- distinguish host reachability from TCP-port availability;
- use `ping`, `telnet`, and modern Windows alternatives appropriately;
- explain how firewall rules affect interface traffic;
- compare FTP with SFTP for file-based interfaces;
- distinguish SOAP from REST web services;
- understand database connectivity through drivers; and
- configure SmartHL7 Viewer with custom Z-segment definitions and encoding.

## 1. Connectivity testing

### Test the host with `ping`

`ping` sends ICMP echo requests to check whether a destination responds:

```powershell
ping 192.0.2.20
```

The address above belongs to a documentation-only range. Use the approved address for the real environment.

A successful ping confirms only that ICMP traffic can travel to the destination and return. It does **not** prove that an HL7 listener is running or that its port is open. A failed ping also does not conclusively prove that the host is unavailable because firewalls often block ICMP.

### Test a port with `telnet`

`telnet` can attempt a TCP connection to a particular IP address and port:

```powershell
telnet 192.0.2.20 2575
```

If the screen clears or the connection opens, the TCP handshake probably succeeded. If Windows reports that it could not open the connection, investigate the destination address, port, listener, route, and firewall rules.

The Telnet Client is optional on Windows and may not be installed. A modern PowerShell alternative is:

```powershell
Test-NetConnection 192.0.2.20 -Port 2575
```

Review the value of `TcpTestSucceeded`.

> A successful port test proves only that a TCP service accepted the connection. It does not confirm MLLP framing, HL7 validation, application routing, message processing, or ACK generation.

### How to interpret combined results

| Ping | TCP-port test | Likely interpretation |
|---|---|---|
| Success | Success | Host and target TCP service are reachable. Continue with an HL7/MLLP test. |
| Success | Failure | Host is reachable, but the service is stopped, the port is wrong, or TCP traffic is blocked. |
| Failure | Success | ICMP is blocked, but the required TCP service is available. |
| Failure | Failure | Addressing, routing, VPN, firewall, server availability, or listener configuration may be wrong. |

## 2. Firewalls

A firewall controls which network traffic may enter or leave a host or network. It can filter traffic by:

- source and destination IP address;
- source and destination port;
- protocol, such as TCP or UDP;
- direction, such as inbound or outbound; and
- network profile, zone, interface, application, or service.

For a TCP-based HL7 interface, the sending system normally initiates the connection and the receiving system listens. This often requires:

- outbound TCP access from the sender;
- inbound TCP access to the receiver;
- an active listener on the agreed destination port; and
- matching permissions on host, network, VPN, and cloud firewalls.

Open only the required traffic. Restrict rules to the agreed protocol, port, direction, and source/destination addresses rather than allowing broad access.

### Firewall troubleshooting checklist

- [ ] Confirm the exact source and destination IP addresses.
- [ ] Confirm the destination port and protocol.
- [ ] Confirm which system initiates the connection.
- [ ] Verify that the receiver is listening on the expected port.
- [ ] Test from the actual interface server, not only from a workstation.
- [ ] Review both host-based and network firewall rules.
- [ ] Check VPN routing and network address translation when applicable.
- [ ] Confirm that test and production rules are configured independently.

## 3. FTP and SFTP connectivity

An FTP/SFTP server provides a central location where clients can upload or download interface files. This approach is useful when the receiving organization does not expose a shared folder or a real-time listener.

Typical file-exchange flow:

1. The sender creates a completed interface file.
2. The sender connects to the file-transfer server.
3. The file is uploaded to the agreed directory.
4. The receiver polls or monitors that directory.
5. The receiver processes and archives the file.
6. Failed files are moved to an error location or retried according to policy.

### FTP versus SFTP

| Feature | FTP | SFTP |
|---|---|---|
| Transport | FTP protocol, normally using separate control and data connections | SSH File Transfer Protocol over one encrypted SSH connection |
| Encryption | Not provided by plain FTP | Encrypts credentials and transferred data |
| Typical port | TCP 21 for control, with additional data ports | TCP 22 by default |
| Firewall behavior | Can be more complex because of active/passive data channels | Usually simpler because one SSH connection is used |
| Recommended for PHI | No, unless protected by an approved secure layer | Preferable when approved and correctly configured |

SFTP is not the same as FTPS. SFTP uses SSH; FTPS is FTP secured with TLS.

### Information to document

- server hostname or IP address;
- port and protocol;
- username and authentication method;
- remote inbound, outbound, archive, and error directories;
- file pattern and naming convention;
- character encoding and line-ending format;
- polling schedule;
- temporary-file or atomic-rename convention;
- duplicate detection and retry behavior; and
- retention, encryption, and audit requirements.

Graphical clients such as WinSCP can help validate connectivity and permissions, but production interfaces should use managed service accounts and automated transfer logic rather than manual transfers.

## 4. Web-service connectivity

Web services commonly communicate over HTTP or HTTPS through an endpoint URL. HTTPS protects data in transit when certificate validation and TLS are configured correctly.

### SOAP

SOAP is a structured messaging protocol commonly associated with XML and a WSDL contract. The WSDL describes available operations, message structures, and service details.

Typical SOAP integration details include:

- endpoint URL;
- WSDL and operation name;
- SOAP action;
- request and response XML schemas;
- authentication method;
- TLS certificate requirements;
- HTTP timeout and retry behavior; and
- SOAP fault handling.

### REST

REST APIs expose resources through URLs and use HTTP methods such as `GET`, `POST`, `PUT`, `PATCH`, and `DELETE`. Payloads are commonly JSON, although XML and other media types are possible.

Typical REST integration details include:

- base URL and resource path;
- HTTP method;
- request headers and `Content-Type`;
- authentication or authorization method;
- request and response schema;
- expected HTTP status codes;
- timeout, retry, and rate-limit behavior; and
- TLS certificate requirements.

### SOAP and REST comparison

| Area | SOAP | REST |
|---|---|---|
| Primary style | Message protocol | Resource-oriented architectural style |
| Common payload | XML | JSON, XML, or other formats |
| Contract | Commonly WSDL | Commonly OpenAPI or equivalent documentation |
| Operation selection | SOAP operation/action | HTTP method and resource URL |
| Error representation | SOAP Fault | HTTP status plus response body |

An HTTP response alone does not guarantee successful healthcare processing. Confirm the application response, business status, correlation identifier, and downstream result.

## 5. Database connectivity

An interface engine may read from or write to a database through an appropriate database driver. The lesson illustrates an application connecting through a driver manager to systems such as Microsoft SQL Server or Oracle Database.

ODBC stands for **Open Database Connectivity**. Java-based engines also commonly use JDBC drivers. The selected driver must match the database product, runtime, and supported version.

### Required database settings

- database type and approved driver;
- server hostname or IP address;
- listener port;
- database or service name;
- username and authentication method;
- required schema and object permissions;
- connection timeout and query timeout;
- connection-pool limits; and
- TLS or wallet/certificate settings where required.

### Security guidance

- Use a dedicated service account with least privilege.
- Grant access only to the required tables, views, or procedures.
- Do not embed credentials in source code or shared documentation.
- Use parameterized SQL rather than string concatenation.
- Protect PHI in transit, at rest, in logs, and in exported files.
- Coordinate transaction, retry, and duplicate-handling behavior.

## 6. End-to-end troubleshooting workflow

1. **Validate the configuration.** Confirm the environment, address, port, protocol, endpoint/path, and credentials.
2. **Verify basic network access.** Check local addressing and routing; use `ping` only when ICMP is permitted.
3. **Verify the destination service.** Confirm that the TCP listener, SFTP service, web server, or database listener is running.
4. **Test the required port.** Use `Test-NetConnection` or an approved equivalent from the sending server.
5. **Inspect security controls.** Review host firewalls, network firewalls, VPNs, proxies, NAT, and certificate trust.
6. **Authenticate.** Verify the service account, key, token, certificate, or database credentials.
7. **Test the application protocol.** Attempt the actual SFTP operation, web request, database query, or MLLP exchange.
8. **Validate the business response.** Inspect the HL7 ACK, HTTP response, SOAP fault, database result, or processed-file status.
9. **Correlate logs.** Compare timestamps, message control IDs, filenames, request IDs, and errors on both systems.
10. **Confirm production readiness.** Test monitoring, timeouts, retries, duplicate prevention, alerting, and recovery procedures.

## 7. Connectivity design record

For every interface, maintain an approved record containing:

| Category | Details to record |
|---|---|
| Systems | Sending system, receiving system, owners, and support contacts |
| Environment | Development, test, staging, or production |
| Network | Source/destination addresses, ports, protocol, direction, VPN, and firewall references |
| Transport | MLLP, SFTP, SOAP, REST, database, or shared folder |
| Security | Authentication, authorization, encryption, certificates/keys, and rotation procedure |
| Data | Message/file format, encoding, schema/version, and PHI classification |
| Reliability | Timeout, retry, acknowledgment, duplicate prevention, archive, and recovery behavior |
| Operations | Monitoring, logging, alerting, retention, escalation, and change ownership |

## Appendix: SmartHL7 Viewer custom definitions

The closing demonstration extracts SmartHL7 Viewer and edits its `.exe.config` file so the viewer can understand organization-specific Z-segments and a custom datatype.

The demonstrated configuration follows this general pattern:

```xml
<?xml version="1.0"?>
<configuration>
  <appSettings>
    <!-- Define custom Z-segments. -->
    <add key="ZS1"
         value="Service ID [SI] | Service type [CE] | Service location [XAD] | Service time [TS] | Note [ST]" />
    <add key="ZL1"
         value="Address [XAD] | Building [ST] | Level [ST] | Room [ST]" />
    <add key="ZL2"
         value="Location [MYDT] | Note [ST]" />

    <!-- Define the custom datatype used above. -->
    <add key="MYDT"
         value="Building | Level | Room number | Shelf number" />

    <!-- Optional encoding for a different language. -->
    <add key="encoding" value="windows-1251" />
  </appSettings>
</configuration>
```

The lesson also shows datatype reminders such as:

- `DT` — date;
- `ST` — string;
- `ID` — coded value from a defined table;
- `NM` — numeric; and
- `SN` — structured numeric, used for qualified numeric comparisons.

### Configuration cautions

- Back up the original configuration file before editing it.
- Ensure the XML remains well formed.
- Use segment names beginning with `Z` only for agreed local extensions.
- Confirm that each component datatype matches the implementation specification.
- Restart the viewer after changing its configuration.
- Treat the viewer configuration as a display aid; it does not alter the message sent by the source system.
- Character encoding must match the actual message encoding. Do not select an encoding only because the file opens without an error.

## Key takeaway

Connectivity must be proven progressively: reach the host, reach the required service port, authenticate, complete the application-level exchange, and verify the business result. Use secure transports and least-privilege access whenever healthcare data is involved.
