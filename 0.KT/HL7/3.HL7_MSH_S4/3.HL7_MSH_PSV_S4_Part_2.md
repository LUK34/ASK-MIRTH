# HL7 Message Segments — MSH and PID (Part 2)

> Structured study notes prepared from **HL7_MSH_PSV_Part 2.mp4**. The recording continues the MSH segment, demonstrates sender/receiver and processing values using an ADT message, explains acknowledgement-condition codes, and introduces the PID patient-identification segment.

## Learning objectives

After completing this lesson, you should be able to:

- map MSH-3 through MSH-6 to the sending and receiving systems;
- distinguish development, testing, and production processing modes;
- interpret acknowledgement-condition codes `AL`, `ER`, `NE`, and `SU`;
- recognize the later MSH fields, including responsible organizations and network addresses;
- explain the purpose of the PID segment;
- identify the main PID fields used for patient identifiers and demographics;
- parse composite and repeating values from a realistic ADT message;
- recognize fields that are withdrawn, retained for compatibility, or profile-dependent.

## 2. MSH recap

MSH is the mandatory first segment of an HL7 v2 message. It tells the receiver how to parse, route, validate, and acknowledge the message.

```hl7
MSH|^~\&|PM|Apollo Hospital|EHR|Apollo Hospital|20151211121701||ADT^A28|2015120604280269714011|D|2.3.1|||AL|AL
```

This example is reconstructed and normalized from the message displayed in the lesson. The source screen contains additional fields and segments.

### Important MSH positions

| Field | Name | Example | Purpose |
|---|---|---|---|
| `MSH-1` | Field Separator | `|` | Separates fields |
| `MSH-2` | Encoding Characters | `^~\&` | Declares component, repetition, escape, and subcomponent separators |
| `MSH-3` | Sending Application | `PM` | Source application |
| `MSH-4` | Sending Facility | `Apollo Hospital` | Source organization/site |
| `MSH-5` | Receiving Application | `EHR` | Destination application |
| `MSH-6` | Receiving Facility | `Apollo Hospital` | Destination organization/site |
| `MSH-7` | Date/Time of Message | `20151211121701` | Message creation timestamp |
| `MSH-9` | Message Type | `ADT^A28` | Message family and trigger event |
| `MSH-10` | Message Control ID | Unique value | Message tracking and ACK correlation |
| `MSH-11` | Processing ID | `D`, `T`, or `P` | Environment/mode |
| `MSH-12` | Version ID | e.g. `2.3.1` | HL7 version used to interpret the message |
| `MSH-15` | Accept Acknowledgment Type | `AL` | Commit/accept ACK preference |
| `MSH-16` | Application Acknowledgment Type | `AL` | Application ACK preference |

### MSH numbering reminder

MSH is special:

```text
MSH|^~\&|PM|Apollo Hospital|EHR|Apollo Hospital
   ↑ ↑    ↑  ↑               ↑   ↑
   1 2    3  4               5   6
```

- The first `|` is MSH-1.
- `^~\&` is MSH-2.
- `PM` is MSH-3.

Do not count `PM` as MSH-2.

## 3. Sending and receiving systems

The video maps the example route as follows:

```text
PM (Apollo Hospital)  ──────────>  EHR (Apollo Hospital)
```

| Location | Video example | Meaning |
|---|---|---|
| MSH-3 | `PM` | Sending application |
| MSH-4 | `Apollo Hospital` | Sending facility |
| MSH-5 | `EHR` | Receiving application |
| MSH-6 | `Apollo Hospital` | Receiving facility |

The application and facility are different concepts:

- **Application** identifies the software system, such as PM, EHR, LIS, RIS, Mirth, or a device system.
- **Facility** identifies the organization, hospital, clinic, branch, or site responsible for the system.

These fields are commonly used by an interface engine for routing, source validation, audit metadata, and destination selection.

## 4. MSH-11 — Processing ID

The video explains these values:

| Value | Environment |
|---|---|
| `D` | Development |
| `T` | Testing/Training |
| `P` | Production |

The receiver should validate MSH-11. A development or test message should not update genuine production patient records merely because it reached a production listener.

Example Mirth validation:

```javascript
var processingId = msg['MSH']['MSH.11']['MSH.11.1'].toString();

if (processingId !== 'P') {
    throw 'Rejected non-production message. MSH-11=' + processingId;
}
```

Whether to reject, quarantine, or reroute the message depends on the interface agreement.

## 5. Acknowledgement-condition codes

The video opens HL7 table **0155 — Accept/Application Acknowledgment Conditions** and shows four values:

| Code | Meaning |
|---|---|
| `AL` | Always |
| `ER` | Error/reject conditions only |
| `NE` | Never |
| `SU` | Successful completion only |

These codes are used in MSH-15 and MSH-16.

### MSH-15 versus MSH-16

- **MSH-15 — Accept Acknowledgment Type:** requests an acknowledgement that the messaging infrastructure accepted or committed the message.
- **MSH-16 — Application Acknowledgment Type:** requests an acknowledgement of application-level processing.

For example:

```hl7
MSH|^~\&|PM|Apollo Hospital|EHR|Apollo Hospital|20151211121701||ADT^A28|MSG00001|P|2.5.1|||AL|ER
```

This requests:

- an accept acknowledgement always (`MSH-15 = AL`);
- an application acknowledgement only when the application encounters an error or rejection (`MSH-16 = ER`).

Actual ACK behavior must be agreed between the sender and receiver. Some interfaces use original-mode acknowledgements and do not implement the enhanced acknowledgement model fully.

### Control-ID correlation

An ACK normally returns the original control ID in MSA-2:

```text
Original MSH-10: MSG00001
ACK MSA-2:       MSG00001
```

This relationship is essential for delivery tracking and troubleshooting.

|---|---|---|---|
| `MSH-22` | Sending Responsible Organization | XON | Organization responsible for sending |

## 7. PID — Patient Identification Segment

The video defines PID as the segment containing information used to identify a patient record.

```hl7
PID|1||8169876^^^MRN~00081694^^^SYSID||TestDaniel^AMARI^A|ARLEEN|20150104|M
```

The PID segment can contain:

- one or more patient identifiers;
- patient name;
- mother's maiden name;
- date of birth;
- administrative sex;
- address and telephone information;
- language, marital status, religion, and ethnicity;
- account and legacy identification details;
- multiple-birth information.

Patient identity is safety-critical. A mapping error can associate clinical information with the wrong person.

### Meaning of the table columns

| Column | Meaning |
|---|---|
| SEQ | Field number, such as PID-3 |
| LENGTH | Maximum length in the referenced version/profile |
| DT | HL7 datatype |
| OPT | Optionality or compatibility status |
| RPT/# | Whether the field repeats and its limit, when specified |
| TBL# | Associated HL7 code table |
| NAME | Standard field name |

The screen uses markers such as `R`, `O`, `W`, and `B`. In general:

- `R` — required by the referenced definition;
- `O` — optional;
- `W` — withdrawn in that version;
- `B` — retained for backward compatibility.

A local implementation profile can impose stricter requirements.

## 9. PID-3 — Patient Identifier List

PID-3 is one of the most important fields in the segment. Its datatype is CX, a composite identifier.

Conceptual format:

```text
ID number ^ check digit ^ check-digit scheme ^ assigning authority ^ identifier type ^ assigning facility
```

Example:

```hl7
PID|1||8169876^^^APOLLO^MR~00081694^^^SYSID^PI||...
```

This contains two repeated identifiers separated by `~`:

| Repetition | ID | Assigning authority | Type |
|---|---|---|---|
| 1 | `8169876` | `APOLLO` | `MR` |
| 2 | `00081694` | `SYSID` | `PI` |

Do not compare identifier numbers alone. The assigning authority and identifier type help establish the identifier's namespace and meaning.

For KNG interfaces, a military number, civil ID, MRN, device ID, or system UID should be clearly distinguished through the agreed CX components rather than placed into an ambiguous unqualified value.

## 10. PID-5 — Patient Name

PID-5 uses the XPN datatype and may repeat.

Simplified structure:

```text
Family name ^ given name ^ second/additional given names ^ suffix ^ prefix
```

Example:

```hl7
PID|...||...||TEST^PATIENT^ONE||...
```

The precise component structure depends on the declared HL7 version. Do not assume that a complete name is a single string.

For bilingual English/Arabic names:

- agree how repetitions or character-set representation will distinguish the scripts;
- preserve the source spelling;
- declare and transmit the correct character encoding;
- do not transliterate automatically unless the interface specification requires it.

## 11. PID-7 and PID-8

### PID-7 — Date/Time of Birth

Common example:

```text
19880625
```

This represents `1988-06-25`. Avoid silently inventing missing month, day, or timezone information when the source provides partial precision.

### PID-8 — Administrative Sex

The example message shows:

```text
M
```

Use codes supported by the declared version and the receiving profile. Do not replace an unknown or unavailable value with an assumed value.

## 12. PID-11, PID-13, and PID-14

These fields are composites and may repeat:

- **PID-11 / XAD:** street, city, state/province, postal code, country, and address type.
- **PID-13 / XTN:** home/personal telephone or telecommunications details.
- **PID-14 / XTN:** business telecommunications details.

Modern HL7 v2 versions allow XTN to represent more than a telephone number, including email and other telecommunication data. Use the proper components and equipment/use codes rather than placing several unrelated values into one plain string.

Some displayed values are difficult to read precisely from the recording; the example above is normalized for teaching and must not be treated as a production message specification.

### What the message communicates

1. PM at Apollo Hospital sends an ADT^A28 message to the EHR.
2. MSH identifies the environment, version, message time, and control ID.
3. EVN records the A28 event and event time.
4. PID carries identifiers and demographic data.
5. PV1/PV2 carry visit-related information.
6. GT1 carries guarantor information.
7. IN1/IN2 carry insurance information.


### Basic validation example

```javascript
var controlId = msg['MSH']['MSH.10']['MSH.10.1'].toString();
var messageCode = msg['MSH']['MSH.9']['MSH.9.1'].toString();
var triggerEvent = msg['MSH']['MSH.9']['MSH.9.2'].toString();
var patientId = msg['PID']['PID.3']['PID.3.1'].toString();

if (!controlId) {
    throw 'MSH-10 Message Control ID is required';
}

if (messageCode !== 'ADT' || triggerEvent !== 'A28') {
    throw 'Unsupported message: ' + messageCode + '^' + triggerEvent;
}

if (!patientId) {
    throw 'PID-3 Patient Identifier List is required';
}
```

If PID-3 repeats, production logic must deliberately select the repetition with the expected assigning authority and identifier type. Reading only the first repetition is unsafe unless the interface contract guarantees its meaning.

## 15. Patient-identity validation checklist

- [ ] Confirm MSH-3 through MSH-6 identify approved systems and facilities.
- [ ] Confirm MSH-11 matches the deployed environment.
- [ ] Validate the declared HL7 version in MSH-12.
- [ ] Apply the agreed MSH-15/MSH-16 acknowledgement behavior.
- [ ] Require a unique MSH-10 control ID.
- [ ] Require at least one valid PID-3 identifier.
- [ ] Select identifiers using assigning authority and identifier type.
- [ ] Validate date-of-birth precision and format.
- [ ] Preserve the difference between missing, unknown, and empty values.
- [ ] Validate code fields against the correct HL7 or local table.
- [ ] Confirm UTF-8 handling before exchanging Arabic names.
- [ ] Protect patient identifiers, addresses, and telephone details in logs.
- [ ] Define duplicate and retry behavior.
- [ ] Reject or quarantine ambiguous patient-identity matches.

## 16. Common mistakes

1. **Reversing MSH-3/MSH-4 with MSH-5/MSH-6.** This can break routing.
2. **Confusing the application with the facility.** Software and organization are not the same identifier.
3. **Ignoring MSH-11.** Test data may be processed as production data.
4. **Assuming `AL` simply means success.** In table 0155 it means an acknowledgement is requested always.
5. **Ignoring MSH-10 during ACK processing.** The sender cannot reliably correlate the response.
6. **Using withdrawn PID fields for new development.** Prefer PID-3 and other current version-appropriate fields.
7. **Treating PID-3 as a plain string.** CX contains important namespace and type components.
8. **Using only the first PID-3 repetition blindly.** It might be the wrong identifier domain.
9. **Placing the entire name into PID-5.1.** XPN is composite.
10. **Merging missing and empty values.** In HL7, an omitted value and an explicit null (`""`) can have different meanings.
11. **Mixing versions.** A field valid in a newer version may not exist in the version declared in MSH-12.
12. **Logging full PID segments.** This can expose sensitive personal and medical information.

## 17. Quick revision sheet

- `MSH-3` / `MSH-4` = sending application/facility.
- `MSH-5` / `MSH-6` = receiving application/facility.
- `MSH-11`: `D` development, `T` testing, `P` production.
- Table 0155: `AL` always, `ER` error/reject only, `NE` never, `SU` success only.
- `MSH-15` controls accept ACK preference.
- `MSH-16` controls application ACK preference.
- `MSH-22` through `MSH-25` identify responsible organizations and network addresses in applicable versions.
- PID identifies the patient record.
- `PID-3` is the main patient identifier list.
- `PID-5` is the patient name.
- `PID-7` is date/time of birth.
- `PID-8` is administrative sex.
- `PID-11` is address.
- `PID-13` and `PID-14` carry telecommunications information.
- Do not use withdrawn fields for new mappings without a compatibility requirement.
