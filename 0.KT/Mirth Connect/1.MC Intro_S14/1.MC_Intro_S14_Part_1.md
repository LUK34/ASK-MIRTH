# Mirth Connect Introduction — Part 1

## Overview

This lesson introduces **Mirth Connect** as a healthcare integration engine. It explains what the platform is used for, the healthcare and general-purpose message formats it can process, its connector options, the Mirth Connect Administrator, and the basic architecture of a channel.

The session objectives also mention channel patterns and installation. In this Part 1 recording, the detailed content concludes with channel architecture; installation is therefore not documented as a completed procedure here.

## Learning objectives

After completing this lesson, you should be able to:

- explain the purpose of Mirth Connect;
- identify common healthcare message formats supported by an integration engine;
- recognize the principal connector types available to a channel;
- describe the purpose of the Administrator dashboard;
- distinguish inbound source processing from outbound destination processing; and
- explain the roles of connectors, filters, validation, and transformers.

## 1. What is Mirth Connect?

Mirth Connect is an integration engine used to exchange, route, transform, and monitor data between systems. In healthcare, it commonly sits between applications such as:

- electronic health record systems;
- laboratory information systems;
- radiology systems;
- pharmacy systems;
- billing or insurance systems;
- medical devices; and
- public-health or external partner systems.

Applications often use different formats, transports, identifiers, and business rules. Mirth Connect channels provide a controlled path for receiving data from one system, processing it, and delivering it to one or more destinations.

```text
Source system
    ↓
Source connector
    ↓
Validation, filtering, and transformation
    ↓
One or more destination connectors
    ↓
Destination system(s)
```

## 2. Supported message and data types

The lesson identifies several formats that may be handled by Mirth Connect:

| Format | Typical purpose |
|---|---|
| HL7 v2 | Delimited clinical and administrative messages such as ADT, ORM, ORU, and SIU |
| HL7 v3 | XML-based healthcare messaging models |
| XML | Structured data exchange |
| DICOM | Medical imaging information and workflows |
| X12/EDI | Administrative and financial electronic transactions |
| NCPDP | Pharmacy-related electronic transactions |
| Delimited text | CSV-like or organization-specific text records |

Support for a format does not remove the need for an agreed interface specification. Both parties must still define message versions, required fields, codes, delimiters, character encoding, validation rules, and acknowledgment behavior.

## 3. Included connector types

Connectors determine how data enters or leaves a channel. Connector availability can depend on the installed product version and extensions.

| Connector or capability | Common use |
|---|---|
| MLLP / TCP/IP | Real-time HL7 v2 exchange over a TCP connection |
| HTTP | Calling or exposing HTTP-based endpoints |
| File system | Reading from or writing to local and shared directories |
| Email | Receiving or sending messages through mail protocols |
| JavaScript | Implementing controlled custom processing logic |
| FTP / SFTP | Exchanging files with a remote transfer server |
| Web services | Integrating through SOAP or REST-style services |
| Database | Reading from or writing to databases through a suitable driver |

### Connector selection questions

Before building a channel, confirm:

- which system initiates the connection;
- whether processing is real time or scheduled;
- the protocol, hostname, port, and direction;
- authentication and encryption requirements;
- the input and output data formats;
- acknowledgment or response expectations;
- timeout, retry, and duplicate-handling rules; and
- monitoring, archiving, and retention requirements.

## 4. Enterprise capabilities introduced in the lesson

These capabilities support secure connections, separation of administrative responsibilities, and operational traceability. Exact availability and behavior depend on the deployed Mirth Connect edition and version.

## 5. Mirth Connect Administrator

The **Mirth Connect Administrator** is the management interface used to create, configure, deploy, and monitor integration channels.

The lesson shows the Administrator dashboard displaying channel information such as:

- channel name and current state;
- revision and last-deployed information;
- received messages;
- filtered messages;
- queued messages;
- sent messages;
- errors; and
- active connections.

The Administrator is also used to:

- create and edit channels;
- start, stop, deploy, and undeploy channels;
- observe message flow;
- inspect server and connection logs;
- review errors and queued messages; and
- manage users, settings, alerts, events, and extensions where available.

### Operational caution

Actions such as redeploying or stopping a channel can interrupt message processing. In a production environment, follow change-control procedures and check queues, active connections, and downstream availability before making changes.

## 6. Core channel building blocks

The introductory channel model contains four principal stages.

| Stage | Direction | Responsibility |
|---|---|---|
| Source connector | Inbound | Receives or retrieves data from the source system |
| Filter / validation | Processing | Determines whether a message meets the configured conditions |
| Transformer | Processing | Extracts, maps, normalizes, enriches, or reformats data |
| Destination connector | Outbound | Sends data to a receiving system; a channel can have one or more destinations |

### Source connector

Every channel has one source connector. It defines how the message enters the channel—for example, through an MLLP listener, a polled folder, an HTTP endpoint, or a database reader.

Source configuration commonly includes:

- connector type;
- bind address, host, folder, endpoint, or query;
- port and protocol;
- schedule or listener behavior;
- inbound data type;
- character encoding; and
- response or acknowledgment behavior.

### Filters and validation

Filters decide whether a message should continue through a particular processing path. Validation checks whether data meets expected structural or business requirements.

Examples include:

- process only `ADT^A01` messages;
- route only records for an approved facility;
- reject messages missing a required patient identifier;
- allow a destination only for a particular order type; and
- block known test data from a production destination.

A filtered message is not necessarily an error. It may be an intentional routing decision. Monitoring should distinguish filtered messages from failed messages.

### Transformers

Transformers convert an inbound representation into the form required by subsequent steps or destination systems. Common transformations include:

- mapping one field to another;
- converting codes between systems;
- changing date formats;
- creating or removing segments;
- converting HL7 to XML, JSON, delimited text, or another HL7 structure;
- enriching a message through a lookup; and
- removing information that a destination is not authorized to receive.

JavaScript and E4X are shown in the lesson as mechanisms for accessing and manipulating message data. E4X appears in older Mirth Connect implementations and training materials; script compatibility should always be checked against the deployed Mirth Connect and Java versions.

### Destination connectors

A channel can contain one or more destination connectors. Each destination can apply its own routing decision and transformation before transmitting the message.

For example, one inbound laboratory order could be:

- sent to the laboratory system through MLLP;
- archived to a file;
- recorded in a database; and
- forwarded to a monitoring service through HTTP.

Each destination should have independent error handling, retry behavior, queue settings, and security controls.

## 7. Source and destination processing

The channel architecture diagram separates source-side processing from destination-side processing.

### Source side

The source connector receives the original message. Source-side validation, filtering, and transformation prepare a common internal or transformed representation for the channel.

### Destination side

Each destination works from the channel's transformed message and can apply destination-specific filtering and transformation. This permits one inbound message to be adapted differently for several receiving systems.

### Message representations

During processing, it is useful to distinguish:

- **raw message** — the data exactly as received;
- **transformed message** — the result after source-side mapping;
- **encoded message** — the serialized form prepared for a destination; and
- **response** — the ACK or other reply returned by the destination.

When troubleshooting, confirm which representation is shown in the message browser before comparing it with the source or destination specification.

## 8. Example channel design

Consider an EHR sending HL7 laboratory orders to a laboratory system:

| Channel component | Example responsibility |
|---|---|
| Source connector | Listen for HL7 over MLLP on an approved TCP port |
| Source validation | Confirm that the message is parseable and required identifiers exist |
| Source filter | Accept only the agreed order message types |
| Source transformer | Normalize identifiers, dates, codes, and required segments |
| Destination filter | Route orders only to the appropriate laboratory |
| Destination transformer | Apply the laboratory-specific format and codes |
| Destination connector | Send the encoded HL7 message to the laboratory MLLP listener |
| Response handling | Capture and interpret the returned HL7 ACK |

## 9. Initial channel-design checklist

- [ ] Source and destination system owners are identified.
- [ ] The interface specification and message version are approved.
- [ ] The source connector and transport direction are confirmed.
- [ ] Network addresses, ports, firewall rules, and certificates are approved.
- [ ] Input and output data types are configured correctly.
- [ ] Required validation and filter rules are documented.
- [ ] Every field and code transformation is traceable to a requirement.
- [ ] Each destination has defined queue, retry, timeout, and error behavior.
- [ ] ACK or application-response processing is documented.
- [ ] Test data is synthetic or appropriately de-identified.
- [ ] Logs do not expose credentials or unnecessary patient information.
- [ ] Monitoring and escalation procedures are ready before production deployment.

## Key takeaway

A Mirth Connect channel is a managed data-processing pipeline. It receives data through one source connector, validates and transforms the message, applies routing rules, and delivers the appropriate representation through one or more destination connectors. Reliable implementations depend as much on monitoring, error handling, security, and a clear interface specification as they do on the channel configuration itself.
