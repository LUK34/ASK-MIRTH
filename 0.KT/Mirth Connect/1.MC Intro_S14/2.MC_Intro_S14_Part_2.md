# Mirth Connect Introduction — Part 2

## Overview

This lesson continues the Mirth Connect introduction by examining the Administrator, channel processing architecture, and common channel-design patterns. It explains how data moves from a source connector through filters and transformers to one or more destination connectors, then introduces four patterns:

- integration;
- broadcast;
- router; and
- channel chaining.

These patterns are conceptual building blocks. A production interface may combine them, but every additional route or dependent channel increases the need for clear ownership, monitoring, error handling, and traceability.

## Learning objectives

After completing this lesson, you should be able to:

- identify the main components of a Mirth Connect channel;
- explain source-side and destination-side processing;
- distinguish filtering from transformation;
- understand how one channel can deliver to multiple destinations;
- compare integration, broadcast, router, and chaining patterns; and
- select a suitable pattern for a healthcare interface requirement.

## 1. Mirth Connect Administrator

The Mirth Connect Administrator is used to define and manage data interfaces. Its dashboard provides a centralized view of deployed channels and their message activity.

Typical dashboard information includes:

- channel state;
- revision and deployment details;
- messages received;
- messages filtered;
- messages queued;
- messages sent;
- messages that ended in error; and
- active or idle connections.

Administrators use this interface to:

- create and configure channels;
- deploy, start, stop, and undeploy channels;
- monitor message flow;
- investigate queued, filtered, and failed messages;
- inspect server and connection logs; and
- manage channel groups and environment settings.

### Production caution

Stopping or redeploying a channel can interrupt message processing. Before changing a production channel, review its queue, active connections, current errors, dependent systems, and rollback plan.

## 2. Channel components

The lesson represents a channel using four principal component types:

| Symbol | Component | Purpose |
|---|---|---|
| `S` | Source connector | Receives or retrieves inbound data |
| `F` | Filter and validation | Decides whether processing should continue |
| `T` | Transformer | Extracts, maps, enriches, or reformats data |
| `D` | Destination connector | Sends outbound data to a destination |

A channel has one source connector and may have one or more destination connectors.

```text
Source system
    ↓
Source connector
    ↓
Source filtering / validation
    ↓
Source transformation
    ↓
Destination-specific filtering / transformation
    ↓
Destination connector(s)
    ↓
Receiving system(s)
```

## 3. Source-side processing

### Source connector

The source connector is the channel entry point. It defines how the channel receives data, such as:

- an MLLP/TCP listener;
- an HTTP receiver;
- a polled file or SFTP directory;
- an email mailbox;
- a database query; or
- another Mirth Connect channel.

Important source settings include the transport, inbound data type, character encoding, polling or listener behavior, response mode, connection limits, and error handling.

### Source filter and validation

Source rules determine whether a message should continue into the channel. Typical checks include:

- accepted HL7 message type and trigger event;
- required identifiers and segments;
- sending facility or application;
- environment or test-message indicators;
- structural validity; and
- agreed business conditions.

A message intentionally rejected by a filter should be distinguished from a message that fails because of an error.

### Source transformer

The source transformer creates a normalized representation that can be used by downstream destinations. It may:

- extract fields;
- standardize identifiers and codes;
- convert dates and units;
- add or remove segments;
- perform controlled lookups;
- populate channel variables; and
- convert between data representations.

The lesson refers to message access through JavaScript and E4X. E4X is associated with older Mirth Connect scripting environments; compatibility must be verified against the deployed Mirth Connect and Java versions.

## 4. Destination-side processing

Each destination can contain its own filter, transformer, and connector configuration.

### Destination filter

A destination filter decides whether a particular destination should receive the message. This enables conditional routing without rejecting the message from every other destination.

For example:

- route laboratory orders to the laboratory destination;
- route radiology orders to the radiology destination;
- archive every message regardless of clinical department; and
- send alerts only for high-priority results.

### Destination transformer

A destination transformer prepares data for one receiving system. Different destinations can require different field mappings, code sets, message structures, or output formats.

### Destination connector

The connector delivers the prepared message. Possible destination types include TCP/MLLP, file writer, SFTP, HTTP sender, web service, database writer, email sender, or channel writer.

Each destination should define:

- queue behavior;
- connection and response timeout;
- retry interval and maximum attempts;
- response or ACK processing;
- error state and recovery procedure; and
- duplicate-prevention strategy.

## 5. Message representations

During channel execution, a message can exist in several forms:

| Representation | Meaning |
|---|---|
| Raw | Data exactly as received from the source |
| Parsed | Data interpreted according to the configured inbound type |
| Transformed | Data after source or destination mapping logic |
| Encoded | Serialized outbound data prepared for transmission |
| Response | Data returned by the destination, such as an HL7 ACK or HTTP response |

When diagnosing a mapping problem, confirm which representation is being inspected. A correct transformed message can still fail during encoding or delivery.

## 6. Channel pattern: Integration

The **integration pattern** is a direct one-source-to-one-destination flow.

```text
One source → filter → transformer → one destination
```

### Example

An EHR sends an HL7 order to Mirth Connect. The channel validates and transforms it, then writes the required data to a database.

### When to use it

- only one destination requires the message;
- routing logic is simple;
- the interface has one clear transformation path; or
- the channel performs a focused receive-transform-deliver operation.

### Benefits

- simple to understand and support;
- straightforward error ownership; and
- fewer partial-success scenarios.

## 7. Channel pattern: Broadcast

The **broadcast pattern** receives a message once and distributes it to multiple destinations. A shared source transformation can prepare a common representation before delivery branches.

```text
                    ┌→ destination A
One source → common ├→ destination B
 transformation    └→ destination C
```

### Example

An ADT message is received once and sent to a laboratory system, pharmacy system, billing system, and clinical data repository.

### When to use it

- every destination should normally receive the same event;
- a common transformation can be reused; and
- each destination can be monitored and retried independently.

### Important behavior

A successful send to one destination does not mean all destinations succeeded. Decide whether destinations are independent or whether the overall business process requires all of them to complete.

### Operational controls

- monitor each destination separately;
- retain correlation identifiers across all copies;
- prevent one slow destination from blocking unrelated routes;
- define destination-specific retry policies; and
- document how partial success is reconciled.

## 8. Channel pattern: Router

The **router pattern** evaluates destination-specific conditions and sends a message only to the destinations whose conditions match.

```text
                    ┌→ route A when condition A is true
One source → routing├→ route B when condition B is true
                    └→ route C when condition C is true
```

Each route may have its own destination filter and transformer.

### Example

An inbound order is routed according to service type:

- laboratory orders go to the LIS;
- radiology orders go to the RIS;
- pharmacy orders go to the pharmacy system; and
- unsupported order types go to an exception workflow.

### Router considerations

- Determine whether routes are mutually exclusive or whether several may match.
- Provide an explicit default or unmatched-message path.
- Keep routing rules readable and traceable to business requirements.
- Test overlapping, missing, null, and unexpected values.
- Record why a route was selected or skipped without exposing unnecessary PHI.

## 9. Channel pattern: Chaining

The **chaining pattern** sends output from one channel into another channel. The downstream channel performs an additional focused stage of processing.

```text
Source → Channel A → Channel B → final destination
```

In Mirth Connect, this is commonly implemented with a channel-to-channel mechanism such as a Channel Writer paired with a Channel Reader, depending on the product version and design.

### Example

1. A receiving channel validates and normalizes inbound HL7 messages.
2. It passes the normalized message to a specialist channel.
3. The specialist channel generates a PDF or performs destination-specific delivery.

### When chaining helps

- shared processing must be reused by several interfaces;
- a complex workflow benefits from separation into smaller responsibilities;
- ingestion and delivery require independent deployment or scaling; or
- a canonical message must feed several downstream workflows.

### Risks

- message tracing becomes more complex;
- acknowledgments and error ownership may become ambiguous;
- synchronous chains can increase latency and failure coupling;
- retries at several levels may create duplicates; and
- changes to a shared channel may affect many dependents.

Pass a stable correlation identifier through every channel, document dependencies, and prevent circular channel chains.

## 10. Pattern comparison

| Pattern | Delivery behavior | Best suited for | Main risk |
|---|---|---|---|
| Integration | One source to one destination | Simple point-to-point interfaces | Logic may be duplicated if reused elsewhere |
| Broadcast | One source to several destinations | The same event must reach multiple consumers | Partial success across destinations |
| Router | Conditional delivery to selected destinations | Business-rule-based routing | Overlapping or unmatched routing conditions |
| Chaining | One channel feeds another | Reuse and separation of complex processing | Dependency, tracing, and retry complexity |

## 11. Selecting a pattern

Use these questions during design:

1. Does the message have one destination or several?
2. Should every destination receive it, or only destinations meeting conditions?
3. Is transformation shared, destination-specific, or both?
4. Must destination failures be isolated from one another?
5. Does processing need to be reused by other channels?
6. Is synchronous processing required, or can work be queued?
7. How will acknowledgments and application responses be returned?
8. What happens when only part of the workflow succeeds?
9. How will a message be traced across destinations and chained channels?
10. Where will retries and duplicate prevention be controlled?

## 12. Practical design guidance

- Prefer the simplest pattern that satisfies the requirement.
- Keep reusable normalization on the source side and system-specific mapping close to its destination.
- Give channels and destinations meaningful, environment-aware names.
- Preserve the original message for audit and troubleshooting according to policy.
- Use message control IDs or other stable correlation identifiers.
- Avoid logging credentials or unnecessary patient data.
- Treat filtering as an explicit business outcome, not as an invisible discard.
- Configure queues and retries according to destination behavior.
- Test each destination independently before testing the complete workflow.
- Test failure scenarios, including unavailable systems, timeouts, negative ACKs, and partial broadcast success.

## 13. Review checklist

- [ ] The selected pattern matches the business requirement.
- [ ] Source transport and inbound data type are correct.
- [ ] Validation and filter rules are documented.
- [ ] Source transformations create the expected common representation.
- [ ] Destination-specific mappings are isolated appropriately.
- [ ] Every route has defined success, filtered, queued, and error behavior.
- [ ] An unmatched route is handled deliberately.
- [ ] ACK and response behavior is documented.
- [ ] Retry logic cannot create uncontrolled duplicates.
- [ ] Correlation identifiers survive broadcasts and channel chains.
- [ ] Monitoring can detect partial success and downstream delays.
- [ ] Deployment dependencies and rollback steps are documented.

## Key takeaway

Mirth Connect channels can do more than move a message from one system to another. By combining source processing, destination-specific filters and transformers, and deliberate channel patterns, they can integrate, broadcast, route, or chain healthcare data workflows. The right design keeps those workflows observable, secure, recoverable, and easy to support.
