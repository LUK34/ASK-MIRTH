# Mirth Connect Introduction — Part 3

## Overview

This lesson expands on four common Mirth Connect channel patterns—**Integration**, **Broadcast**, **Router**, and **Chaining**—and explains how to select a pattern from the integration requirements. It also introduces the first steps for obtaining Mirth Connect by selecting an appropriate release and installer.

The emphasis is on designing channels that send each message to the correct systems, handle destination outcomes independently, and remain supportable as message volume and workflow complexity grow.

> **Lesson boundary:** The video begins the download and installation-preparation process, but it does not demonstrate a complete Mirth Connect installation.

## Learning Objectives

After completing this lesson, you should be able to:

- Recognize the four channel patterns discussed in the course.
- Distinguish broadcasting from conditional routing.
- Explain how channels can be chained into reusable processing stages.
- Select a pattern based on message type, destination, department, or facility.
- Account for partial failures, retries, message volume, and monitoring.
- Select the correct Mirth Connect package for a target environment.

## Channel Processing Model

A basic Mirth Connect channel can be viewed as a processing pipeline:

| Stage | Purpose |
|---|---|
| **Source** | Receives or polls for an incoming message. |
| **Filter** | Decides whether a message should continue through a connector. |
| **Transformer** | Parses, maps, enriches, or converts the message. |
| **Destination** | Sends the processed message to another system or workflow. |

The source, filters, transformers, and destinations are arranged differently depending on the selected pattern.

## 1. Integration Pattern

The Integration pattern is the simplest design presented in the lesson. A channel receives a message, applies the required filtering or transformation, and sends the result to one destination.

### Typical flow

1. Receive data from a source system.
2. Validate or filter the message.
3. Transform it into the receiving system's required format.
4. Deliver it to a single destination, such as a database or downstream application.

### When to use it

- One source communicates with one target.
- The transformation logic is straightforward.
- No destination selection or fan-out is required.
- The workflow should remain easy to trace and operate.

### Example

An HL7 message is received, normalized, and written to a clinical database.

## 2. Broadcast Pattern

The Broadcast pattern sends a copy of the same source message to every configured destination. Source processing occurs first, after which each destination can perform its own filtering, transformation, and delivery work.

### Key behavior

- Every intended destination receives a copy of the message.
- Destination connectors can format the copy differently for their target systems.
- Each destination has its own processing result.
- A failure at one destination does not automatically mean that all other destinations failed.

### Healthcare example

An ADT event may need to reach several applications, such as:

- A laboratory system
- A pharmacy system
- A billing system
- A clinical archive

The event is broadcast because every listed system needs the update, even though each one may require a different outbound format.

### Operational consequence

Do not treat a source message as simply “successful” or “failed” without inspecting destination status. A message can be delivered successfully to three systems while failing at a fourth. Monitoring, alerting, and recovery must therefore operate at the destination level.

## 3. Router Pattern

The Router pattern also contains multiple destinations, but it does **not** automatically send every message to every destination. Destination filters or routing conditions select the destination or destinations appropriate for each message.

### Common routing conditions

- HL7 message type, such as ADT or ORM
- Sending facility
- Department or clinical service
- Patient or encounter attributes
- Event type or workflow state
- Other values found in the inbound message or lookup data

### Example

A shared inbound channel receives several kinds of HL7 traffic:

- ADT messages are routed to systems that need patient and encounter updates.
- ORM messages are routed to order-processing systems.
- Facility- or department-specific messages are sent only to the applications responsible for that location.

This prevents unrelated systems from receiving messages they cannot or should not process.

## Broadcast vs. Router

| Question | Broadcast | Router |
|---|---|---|
| Who receives the message? | All configured destinations | Only destinations whose conditions match |
| Main decision | Every target needs a copy | The message content determines the target |
| Destination filters | May refine local processing | Central to destination selection |
| Typical use | Enterprise-wide ADT distribution | Routing by type, facility, or department |
| Main operational risk | Partial destination failure | Incorrect or incomplete routing rules |

A useful design question is: **Does every destination need this event?** If yes, broadcasting may fit. If not, routing conditions are required.

## 4. Chaining Pattern

Chaining connects one Mirth Connect channel to another. The first channel performs an initial stage of processing and forwards its output to a secondary channel, which carries out additional transformation, routing, document generation, or delivery.

### Typical uses

- Separate message normalization from application-specific delivery.
- Reuse a common transformation in several workflows.
- Send normalized data to a specialized departmental channel.
- Generate a report or PDF in a downstream processing stage.
- Divide a complex integration into smaller, focused channels.

### Conceptual example

1. A primary channel receives and validates an HL7 message.
2. It converts the input into a standard internal representation.
3. It forwards the normalized result to a secondary channel.
4. The secondary channel applies department-specific logic and produces a report, PDF, or outbound transaction.

### Design cautions

Chaining improves reuse and separation of concerns, but it also creates more operational dependencies. A production design should:

- Preserve a correlation identifier across channels.
- Define which channel owns retries and error recovery.
- Prevent accidental processing loops.
- Account for duplicate delivery when a retry occurs.
- Record enough metadata to trace a message from the first channel to the last.
- Avoid splitting a simple integration into unnecessary layers.

## Pattern Selection Guide

| Requirement | Suggested starting pattern |
|---|---|
| One source and one destination | Integration |
| Every destination must receive the event | Broadcast |
| Destination depends on message content | Router |
| Processing should be divided into reusable stages | Chaining |

Real integrations can combine these patterns. For example, a router can select a departmental channel, and that downstream channel can broadcast a transformed event to multiple systems.

Before selecting or combining patterns, answer the following questions:

1. Which systems need each message type?
2. Does every destination need every event?
3. Which conditions determine message ownership?
4. Does transformation logic need to be reused?
5. What happens when only one destination fails?
6. Where will retry, recovery, and duplicate prevention occur?
7. How will operations staff trace a message across channels?

## Throughput and Operational Design

A design that works for a small demonstration must also be evaluated against real message volume. When hundreds or thousands of messages move through multiple destinations or chained channels, consider:

- Expected average and peak throughput
- Destination latency and availability
- Queue growth during outages
- Connection and thread limits
- Retry intervals and maximum retry counts
- Duplicate-message handling
- Error queues and manual recovery procedures
- Message retention and log growth
- Alerts for stalled channels and destination failures

Scale should be tested with realistic message sizes, routing conditions, transformations, and downstream response times—not only with a single sample message.

## Download and Installation Preparation

The lesson concludes by opening the GitHub release page for **Mirth Connect 4.5.2** and reviewing downloadable assets. This is the start of installation preparation rather than a complete installation walkthrough.

### Package-selection checklist

1. Confirm the exact Mirth Connect version approved for the environment.
2. Select the package for the target operating system.
3. Confirm whether the host requires a 64-bit or another architecture-specific build.
4. Choose an installer for an interactive setup or an archive when the deployment process requires manual packaging.
5. Review that release's documentation for compatible Java/runtime and database requirements.
6. Verify the download checksum or signature when one is published.
7. Test the package in a non-production environment before production deployment.

> Do not assume that prerequisites are identical across Mirth Connect releases. Confirm Java, database, operating-system, and browser compatibility in the documentation for the exact version being installed.

### Environment-readiness checklist

Before running an installer, prepare:

- A dedicated service account with least-privilege permissions
- The required application, management, and database ports
- Firewall and network routes to source and destination systems
- Database location, credentials, backup policy, and retention requirements
- TLS certificates and the organization's trust chain
- Storage capacity for application data, logs, attachments, and backups
- Monitoring, alerting, and log-forwarding destinations
- A rollback plan and a tested backup procedure

For restricted or disconnected networks, download and validate the approved installer in a connected staging environment, then transfer it through the organization's controlled software-import process.

## Validation Scenarios

Use these scenarios to verify the finished channel design:

### Integration

- A valid message reaches the single destination in the required format.
- A malformed or disallowed message is rejected predictably.

### Broadcast

- All destinations receive their own copy.
- One unavailable destination does not hide the successful outcomes of others.
- Recovery targets only the failed destination when appropriate.

### Router

- Every known message category reaches the correct destination.
- A message matching no rule follows a defined fallback or error path.
- Overlapping rules do not create unintended duplicate delivery.

### Chaining

- The downstream channel receives the expected normalized message.
- Correlation information remains available end to end.
- Failure and retry behavior does not create loops or duplicate business events.

## Key Takeaways

- Use **Integration** for a direct one-source-to-one-destination workflow.
- Use **Broadcast** when every destination needs a copy of the event.
- Use **Router** when message content determines which destination should receive it.
- Use **Chaining** to build reusable, staged workflows, while carefully managing tracing and retries.
- Monitor destination outcomes independently, especially in broadcast designs.
- Choose a Mirth Connect installer only after confirming the release, platform, architecture, and prerequisites.
- Treat installation preparation and production readiness as separate from channel design.
