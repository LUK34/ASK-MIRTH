# Mirth Connect After Installation — Part 1

## Overview

This lesson demonstrates the first activities performed after installing **Mirth Connect on Windows**. It covers launching the Administrator, completing the initial account setup, using the Server Manager, connecting to local or remote Mirth Connect instances, and reading the main Dashboard and message statistics.

The recording uses Mirth Connect 4.5.x screens. Some demonstrations show **4.5.2**, while an existing training environment displays **4.5.0**. Treat the values shown as examples and verify all settings against the version approved for your environment.

## Learning Objectives

After this lesson, you should be able to:

- Recognize the Windows applications installed with Mirth Connect.
- Start or verify the Mirth Connect service.
- Launch the Mirth Connect Administrator.
- Connect through HTTP or HTTPS.
- Complete the first-login administrator profile.
- Review server, logging, and database settings.
- Interpret channel states and Dashboard counters.
- Open a channel's message browser and inspect raw HL7 data.

## 1. Installation and Upgrade Prompt

When the Windows installer detects an existing Mirth Connect installation, it offers two choices:

- **Update the existing installation**
- **Install into a different directory**

Before updating an existing environment:

1. Back up the Mirth Connect database.
2. Export or otherwise back up channels, code templates, configuration, and custom extensions.
3. Record the current version and installation path.
4. Read the upgrade guide and release notes for the target version.
5. Confirm Java, database, operating-system, and extension compatibility.
6. Test the upgrade in a non-production environment.

> Do not use an in-place upgrade as a substitute for a tested backup and rollback plan.

## 2. Windows Components Installed by Mirth Connect

The Windows Start menu can expose several Mirth Connect applications:

| Component | Purpose |
|---|---|
| **Mirth Connect** | Opens or starts the main Mirth Connect entry point. |
| **Mirth Connect Server** | Runs the integration engine server process. |
| **Mirth Connect Administrator Launcher** | Creates saved server connections and downloads/launches the matching Administrator client. |
| **Mirth Connect Server Manager** | Controls the Windows service and exposes server, database, and information settings. |

The exact shortcuts depend on the package and options selected during installation.

## 3. Starting the Server

The Mirth Connect server must be running before the Administrator can connect.

Open **Mirth Connect Server Manager** and use the **Service** tab to check or control the service:

- **Start** — starts the Mirth Connect service.
- **Restart** — restarts the running service.
- **Stop** — stops the service.
- **Refresh** — refreshes the displayed service status.
- **Start Mirth Connect Server Manager on system startup** — controls whether the manager opens when Windows starts.

### Safe operating practice

- Confirm that no critical interfaces are processing messages before restarting or stopping production.
- Notify dependent teams during planned downtime.
- After a restart, verify the service, Administrator login, deployed channels, queues, and destination connectivity.

## 4. Server Manager Tabs

### Service

Controls the Windows service and provides access to the Administrator.

### Server

The lesson shows server-level settings such as:

- HTTP port
- HTTPS port
- Server memory
- Main log level
- Database log level
- Channel log level
- Available Mirth log files

The demonstrated environment displays HTTP port **8090** and HTTPS port **8443**. These are environment-specific values, not universal requirements.

#### Logging guidance

Use more verbose log levels temporarily during diagnosis. Excessive debug logging in production can consume storage, expose sensitive message content, and make important errors harder to locate. Return logging to the approved operational level after troubleshooting.

### Database

The Server Manager can select and configure the database used by the Mirth Connect platform. Options visible in the lesson include:

- Derby
- PostgreSQL
- MySQL
- Oracle
- SQL Server

The embedded Derby database is convenient for learning and local evaluation. For a production deployment, use the database platform approved by the organization and configure its JDBC URL, account, permissions, backups, availability, monitoring, and recovery procedures.

> The database configured here stores Mirth Connect configuration and operational data. It is separate from destination databases that individual channels may read from or write to.

### Info

Provides product or installation information useful when verifying the installed release and diagnosing support issues.

## 5. Administrator Launcher

The **Mirth Connect Administrator Launcher** manages one or more server connections. A connection contains the address of the Mirth Connect server and optional client runtime settings.

### Local connection examples

```text
https://localhost:8443
http://localhost:8090/webstart
```

Use the address and ports configured for your own server. Prefer HTTPS for normal administration, especially across a network.

### Creating a connection

1. Open **Mirth Connect Administrator Launcher**.
2. Select **New**.
3. Enter the server address.
4. Select the appropriate Java runtime option when required.
5. Review heap-size and TLS settings only if the environment requires customization.
6. Save the connection with a descriptive name.
7. Select the connection and click **Launch**.

On first use—or after a server/client version change—the launcher may download the Administrator libraries from the selected Mirth Connect server. It then starts the client that matches that server.

### Multiple environments

Use separate, clearly named launcher entries for development, test, and production, for example:

```text
MIRTH-DEV
MIRTH-UAT
MIRTH-PROD
```

Add a visible environment naming convention to reduce the risk of administering the wrong server.

## 6. First Login and Account Setup

After authentication, a new installation may display a welcome form for the initial administrator account. The screen permits the user to:

- Change the administrator password.
- Enter first name and last name.
- Enter email, country, state or territory, phone, and organization information.
- Select role, business, and other profile details.

### Security requirements

- Replace any initial or temporary password immediately.
- Use a strong, unique password stored according to organizational policy.
- Do not share the administrator account.
- Create named accounts for individual administrators.
- Grant only the privileges required for each role.
- Review accounts and permissions periodically.
- Restrict Administrator access to approved networks or administrative workstations.

## 7. Administrator Dashboard

The Dashboard provides an operational view of deployed channels. The main table includes channel status, name, deployment information, message counters, and connection state.

### Common channel states

| State | Meaning |
|---|---|
| **Started** | The deployed channel is running and can process messages. |
| **Paused** | Message processing is temporarily paused while the channel remains deployed. |
| **Stopped** | The channel is deployed but not running. |
| **Undeployed** | The saved channel configuration is not active on the server. |
| **Mixed** | Connectors or grouped items do not all have the same state. |

Expanding a channel reveals its source and destination connectors, which can have their own status and counters.

## 8. Dashboard Counters

| Counter | Operational meaning |
|---|---|
| **Received** | Messages accepted by the source connector. |
| **Filtered** | Messages rejected by a configured filter. |
| **Queued** | Messages waiting for processing or delivery. |
| **Sent** | Messages successfully sent by a destination connector. |
| **Errored** | Processing or delivery attempts that ended in error. |
| **Connection** | Current connector connection state, when applicable. |

### Interpreting the counters

Counters must be interpreted in the context of the channel design. For example:

- `Received` may be higher than `Sent` when messages are filtered.
- A multi-destination channel can produce several destination results for one received message.
- A non-zero `Queued` value may be normal briefly but concerning if it continues to rise.
- A non-zero `Errored` value requires inspection of the affected messages and connectors.

The Dashboard can display **current statistics** or **lifetime statistics**. Confirm which view is active before comparing counts or reporting a problem.

## 9. Dashboard Actions

Depending on the selected channel and its state, Dashboard tasks include:

- Refresh
- Send Message
- View Messages
- Remove All Messages
- Clear Statistics
- Start
- Pause
- Stop
- Undeploy Channel

### Important distinction

- **Clear Statistics** resets displayed counters; it does not fix failed messages.
- **Remove messages** deletes stored message records and can eliminate evidence needed for troubleshooting or audit.
- **Reprocess** sends a stored message through processing again and can create duplicate downstream transactions.

Use destructive or replay actions only under an approved operating procedure.

## 10. Viewing Channel Messages

Selecting a channel and choosing **View Messages** opens the message browser. The lesson demonstrates:

- Filtering by time range.
- Searching text.
- Filtering by processing status.
- Selecting a source or destination connector.
- Opening stored message records.
- Reviewing raw or transformed content.
- Reviewing mapping and error details.

The displayed example contains an HL7 laboratory result message with segments such as:

```text
MSH
PID
PV1
ORC
OBR
OBX
```

### Message statuses

Search filters can include statuses such as:

- Received
- Transformed
- Filtered
- Queued
- Sent
- Error
- Pending

Use the status, connector, error details, and message content together to identify the exact stage at which processing failed.

## 11. Basic Error-Investigation Workflow

1. Identify the channel with an increasing **Errored** counter.
2. Expand the channel to locate the affected connector.
3. Open **View Messages**.
4. Filter for **Error** and the relevant time window.
5. Select a failed message.
6. Review the **Errors** tab and connector status.
7. Compare raw and transformed content.
8. Check the server and channel logs for the same timestamp.
9. Correct the configuration, data, credential, network, or destination issue.
10. Reprocess only after assessing duplicate-delivery risk.
11. Confirm successful delivery and monitor subsequent traffic.

## 12. Post-Installation Validation Checklist

- [ ] Confirm the installed Mirth Connect version.
- [ ] Confirm the service starts successfully.
- [ ] Verify configured HTTP and HTTPS ports.
- [ ] Confirm host firewall rules and network reachability.
- [ ] Launch the Administrator using the correct server connection.
- [ ] Change the initial password and create named accounts.
- [ ] Verify the configured database and its backup strategy.
- [ ] Review memory and logging configuration.
- [ ] Confirm expected channels are deployed.
- [ ] Verify channel states and destination connections.
- [ ] Send an approved test message.
- [ ] Inspect Received, Filtered, Queued, Sent, and Errored counters.
- [ ] Confirm logs and alerts are available to support staff.
- [ ] Document restart, recovery, and rollback procedures.

## Production Recommendations

- Prefer HTTPS and an organization-managed certificate.
- Do not expose administration ports directly to untrusted networks.
- Use named user accounts and least-privilege roles.
- Use an enterprise-supported database with tested backups.
- Protect logs and stored messages because they may contain sensitive health information.
- Monitor service availability, channel state, queues, errors, disk space, and database health.
- Separate development, test, and production connections clearly.
- Export and version-control approved channel configurations before changes.
- Test upgrades and extensions outside production first.

## Key Takeaways

- The Mirth Connect server must be running before the Administrator can connect.
- The Server Manager controls the service and exposes server, logging, and database configuration.
- The Administrator Launcher can maintain several local or remote server connections.
- The first administrator login should be followed immediately by secure account configuration.
- Dashboard counters show where messages are received, filtered, queued, sent, or errored.
- Troubleshooting begins by identifying the affected connector and inspecting the stored message and error details.
- Reprocessing and message removal can have operational consequences and must be controlled.
