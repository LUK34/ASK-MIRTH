# Mirth Connect After Installation — Part 2

## Overview

This lesson continues the tour of the Mirth Connect Administrator. It explains how to operate channels from the **Dashboard**, inspect connection activity and global maps, filter channels, clear statistics, remove stored messages, and work with the main **Channels** screen. It also introduces channel groups, tags, channel metadata, and the Summary tab's message-storage and pruning settings.

The recording uses Mirth Connect 4.5.0 in a training environment. Channel names, statistics, dates, and identifiers shown in the lesson are examples.

## Learning Objectives

After this lesson, you should be able to:

- Read channel and connector state from the Dashboard.
- Use Dashboard filtering and current/lifetime statistics.
- Review server logs, connection logs, and global maps.
- Understand Start, Stop, Pause, and Undeploy behavior.
- Distinguish clearing counters from deleting stored messages.
- Navigate the Channels screen and interpret its columns.
- Recognize channel groups, data types, tags, IDs, and revisions.
- Use common channel-management actions safely.
- Understand the major settings on a channel's Summary tab.

## 1. Dashboard Structure

The Dashboard displays deployed channels and summarizes their operational state. Expanding a channel reveals its source and destination connectors.

### Main columns

| Column | Meaning |
|---|---|
| **Status** | Current channel or connector state. |
| **Name** | Channel, source connector, or destination connector name. |
| **Rev** | Deployed channel revision. |
| **Last Deployed** | Date and time of the most recent deployment. |
| **Received** | Messages accepted by the source. |
| **Filtered** | Messages rejected by a filter. |
| **Queued** | Messages waiting for processing or delivery. |
| **Sent** | Successful destination sends. |
| **Errored** | Processing or delivery results that ended in error. |
| **Connection** | Connector connection state, such as Idle or Disconnected. |

### Channel states

| State | Operational meaning |
|---|---|
| **Started** | Deployed and able to process messages. |
| **Paused** | Deployed, but normal processing is temporarily suspended. |
| **Stopped** | Deployed but not processing. |
| **Mixed** | The items represented by the row do not share one state. |

An expanded channel can show a stopped source and a started destination, which causes the parent row to appear as **Mixed**.

## 2. Start, Stop, Pause, and Undeploy

The available Dashboard actions depend on the selected channel and its current state.

### Start

Starts a stopped, deployed channel. The source begins accepting or polling for messages according to its connector type.

### Stop

Stops message processing while leaving the channel deployed. Use it when processing must cease but the deployed configuration should remain available.

### Pause

Temporarily pauses a started channel. Depending on connector behavior and configuration, in-flight or queued work may still require attention.

### Undeploy

Removes the active deployed instance from the server while preserving the saved channel definition on the Channels screen.

### Safe control procedure

1. Confirm the selected environment and channel.
2. Check queued messages and current traffic.
3. Identify dependent channels or systems.
4. Record the reason for the action.
5. Perform the approved Start, Stop, Pause, or Undeploy operation.
6. Verify the resulting state and connection status.
7. Monitor new errors or queue growth after restoration.

## 3. Filtering the Dashboard

The Dashboard filter can reduce the displayed rows by channel name or tag. This is useful when a server contains many channel groups and deployed integrations.

Examples of useful tags include:

```text
ADT
LAB
DICOM
PROD
TEST
FACILITY_A
```

Tags should follow a documented naming convention. Use them to identify business domain, message family, facility, environment, or support ownership without embedding every attribute in the channel name.

Clearing the filter restores the complete Dashboard view.

## 4. Current vs. Lifetime Statistics

The Dashboard provides two statistical views:

- **Current Statistics** — counts accumulated since the latest statistics reset or relevant runtime boundary.
- **Lifetime Statistics** — longer-term totals retained by the platform.

Before reporting counts, always verify which option is selected. Two users can see different-looking totals for the same channel if they are comparing different views.

## 5. Clear Statistics

**Clear Statistics** resets the displayed counters for the selected channel or channels. It is useful when beginning a controlled test and a clean baseline is required.

Clearing statistics:

- Does not correct the underlying cause of an error.
- Does not automatically remove stored messages.
- Can erase an important operational baseline.
- Can make incident comparison difficult if performed without documentation.

### Recommended use

1. Capture the current counts or a screenshot.
2. Confirm that monitoring and audit requirements permit a reset.
3. Select only the intended channel.
4. Clear the counters.
5. Send or receive the controlled test message.
6. Refresh and compare the new results.

## 6. Remove All Messages

**Remove All Messages** deletes stored messages for the selected channel or channels, including queued messages when confirmed by the dialog. The interface requires an explicit confirmation phrase such as `REMOVEALL`.

The confirmation options may include:

- Include selected channels that are not stopped; the application temporarily stops them during removal.
- Clear statistics for the affected channels.

### Why this is high risk

Removing messages can destroy:

- Queued transactions that have not reached their destination.
- Failed-message evidence required for troubleshooting.
- Raw and transformed payloads needed for audit.
- Metadata needed to correlate an incident.
- The source material required for later reprocessing.

### Production rule

Do not remove messages merely to make an error counter disappear. First determine the retention, audit, clinical, and recovery consequences. Export required evidence and obtain approval before deletion.

## 7. Lower Dashboard Panels

### Server Log

Shows server runtime information, such as startup details, web-server addresses, Java runtime information, and platform messages. Use it to confirm server startup and locate application-level warnings or errors.

### Connection Log

Shows connector connection events with information such as:

- Timestamp
- Channel
- Connector information
- Event state
- Additional details

Typical events include **Idle** and **Disconnected**. Repeated disconnections can indicate listener, network, destination, credential, or endpoint problems.

### Global Maps

Displays globally available key/value entries. Global map values can be shared across integrations, so changes must be controlled carefully. Do not store secrets in plain text unless the platform's approved secure mechanism is being used.

## 8. Navigating the Channels Screen

The **Channels** screen contains saved channel definitions, whether or not they are currently deployed.

### Main columns

| Column | Meaning |
|---|---|
| **Status** | Whether the saved channel is enabled or disabled. |
| **Data Type** | The inbound or configured message representation, such as HL7 v2.x, XML, JSON, Raw, DICOM, or Delimited Text. |
| **Name** | Channel name. |
| **Rev** | Revision associated with the deployed configuration when applicable. |
| **Id** | Globally unique channel identifier. |
| **Local Id** | Server-local numeric identifier. |
| **Description** | Documentation stored with the channel. |
| **Last Deployed** | Most recent deployment time. |
| **Last Modified** | Most recent saved modification time. |

### Enabled vs. deployed

An **enabled** saved channel is permitted to run when deployed. Deployment makes the configuration active on the server. Therefore, Enabled/Disabled and Deployed/Undeployed describe related but different conditions.

## 9. Channel Groups

Groups organize channels into logical collections. A server can group integrations by:

- Application
- Facility
- Department
- Interface family
- Environment
- Support team
- Project or release

Channels not assigned to a custom group can appear under a default group.

### Group operations shown

- Assign To Group
- New Group
- Import Group
- Export All Groups

Group names improve navigation but should not replace channel-level documentation, ownership, or dependency records.

## 10. Channel Tasks

Depending on the selected row, the Channels screen exposes actions such as:

| Action | Purpose |
|---|---|
| **Refresh** | Reloads the channel list. |
| **Redeploy All** | Deploys the latest saved definitions for all applicable channels. |
| **Debug Channel** | Opens a diagnostic execution workflow. |
| **Deploy Channel** | Activates the selected saved channel definition. |
| **Edit Global Scripts** | Manages scripts shared by channels. |
| **Edit Code Templates** | Manages reusable code templates. |
| **New Channel** | Creates a channel. |
| **Import Channel** | Imports a channel definition. |
| **Export Channel / Export All Channels** | Exports channel configuration for backup or migration. |
| **Delete Channel** | Deletes the saved channel definition. |
| **Clone Channel** | Creates a copy for controlled reuse or development. |
| **Edit Channel** | Opens the selected channel for configuration. |
| **Enable/Disable Channel** | Controls whether the channel is eligible to run. |
| **View Messages** | Opens stored messages for the selected channel. |

### Change-control warning

Actions such as Redeploy All, Delete Channel, Disable Channel, and shared-script changes can affect several interfaces. Use versioned exports, peer review, environment confirmation, and a rollback procedure.

## 11. Channel Identity and Revision

A Mirth Connect channel can expose several identifiers:

- **Channel name** — human-readable label.
- **Id** — unique channel UUID used to identify the channel consistently.
- **Local Id** — shorter identifier assigned by the server.
- **Revision** — version of the channel configuration.

Do not rely only on the channel name during migration or automation because names can be changed or duplicated in another environment. Preserve the channel UUID and document any environment-specific identity differences.

## 12. Editing a Channel: Summary Tab

The lesson opens an existing channel and displays the **Summary** tab.

### Channel properties

Important fields include:

- Name
- Enabled flag
- Data Types
- Dependencies
- Initial State
- Attachment mode
- Tags
- Clear global channel map on deploy
- Store Attachments
- Channel description

### Initial state

The initial state controls how the channel behaves after deployment, such as starting immediately or remaining stopped/paused according to the selected option. Choose it based on operational requirements and deployment procedure.

### Dependencies

Dependencies define ordering relationships between channels. Use them when one channel must be deployed or started before another, but avoid unnecessary coupling.

## 13. Message Storage

The Summary screen includes message-storage settings for metadata, content, attachments, and custom metadata.

Possible controls include:

- Amount of message content retained
- Metadata retention
- Durable message delivery
- Encrypt message content
- Store or remove attachments
- Remove message content on completion
- Preserve content only for filtered messages

Storage choices affect troubleshooting, auditability, performance, database size, and privacy.

### Design trade-off

| More retention | Less retention |
|---|---|
| Better troubleshooting and replay evidence | Lower database and storage consumption |
| Stronger historical traceability | Reduced exposure of sensitive message content |
| Easier incident investigation | Less content available after completion |
| Higher capacity and retention requirements | Greater dependence on external logging or archives |

## 14. Message Pruning

Pruning removes old metadata or content according to configured retention rules. Options shown include storing metadata indefinitely or pruning it after a number of days, and pruning content when metadata is removed or after a specified age.

The interface notes that incomplete, errored, and queued messages are not treated like completed messages under the normal pruning rule.

Before configuring pruning:

1. Determine clinical and legal retention requirements.
2. Estimate daily volume and storage growth.
3. Decide how long raw and transformed content is required.
4. Protect messages needed for unresolved incidents.
5. Confirm database backups and restoration procedures.
6. Test pruning in a non-production environment.
7. Monitor database size and pruning completion.

## 15. Custom Metadata

Custom metadata adds searchable columns derived from mapped variables. The lesson shows example columns such as `SOURCE` and `TYPE` mapped to variables.

Custom metadata can make message searches faster and more useful for support teams, for example:

```text
MESSAGE_TYPE
FACILITY
PATIENT_ID
ORDER_NUMBER
SOURCE_SYSTEM
DESTINATION_SYSTEM
```

Avoid indexing unnecessary or highly sensitive values. Each custom metadata field increases storage and may expose data to users who can browse messages.

## Operational Checklist

### Before changing a channel state

- [ ] Confirm server and environment.
- [ ] Confirm channel name and UUID.
- [ ] Check queues and active traffic.
- [ ] Review dependencies.
- [ ] Record current state and counters.

### Before clearing statistics

- [ ] Capture existing counts.
- [ ] Confirm monitoring implications.
- [ ] Select only the intended channel.
- [ ] Document the reset time and reason.

### Before removing messages

- [ ] Stop or safely isolate processing.
- [ ] Identify queued and errored messages.
- [ ] Export evidence required for recovery or audit.
- [ ] Assess downstream duplicate and data-loss risk.
- [ ] Obtain required approval.
- [ ] Verify the selected channels carefully.

### Before deploying or redeploying

- [ ] Export the current working configuration.
- [ ] Peer-review the proposed change.
- [ ] Confirm dependencies and shared scripts.
- [ ] Prepare rollback steps.
- [ ] Deploy in the approved maintenance window.
- [ ] Validate traffic, counters, queues, and logs.

## Key Takeaways

- The Dashboard represents deployed runtime behavior; the Channels screen represents saved channel definitions.
- Expand a channel to understand connector-level state and statistics.
- Dashboard filters and tags make large environments easier to operate.
- Current and lifetime statistics are different views and must not be confused.
- Clearing statistics resets counters; removing messages deletes stored operational data.
- Message removal, channel deletion, and broad redeployment require strict change control.
- Channel groups, descriptions, tags, and custom metadata improve supportability when governed consistently.
- Message retention and pruning must balance troubleshooting, performance, privacy, and regulatory needs.
